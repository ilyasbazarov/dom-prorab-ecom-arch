# BRIEF F4-17 — Прогон шестнадцати шагов карты без 1С и эквайринга: чем проверено, а не что заказано
**Тип:** verification
**Суждение:** механический (ADR-029 §4). Ожидаемое поведение каждого шага уже названо нормативно и
по адресу — поля «Вызов или событие», «Ответ» и «Что меняется после» шага `OF-NN` карты
`l0-canon/order_flow_e2e.md` §1. Исполнитель сверяет факт с этим ожиданием и НИЧЕГО не формулирует
сам: место, где требуемое поведение не названо по адресу, есть стоп и Architect, а не повод
дописать (ADR-132 §2).
**Класс задачи:** A, с одним изъятием. Шаг `OF-20` создаёт РЕАЛЬНУЮ заявку на доставку в Яндексе —
это выезд курьера и деньги наружу; при сомнении в классе класс B (`CLAUDE.md` §Мандат), поэтому
шаг исполняется только после отдельного подтверждения Owner. Перечень класса B здесь не
дублируется.
**Роль:** Executor (Sonnet), путь Claude Code · **Дата:** 2026-08-11 · **Автор:** Architect
**Служит:** Ф-1 и Ф-2 (`l0-canon/project_goal.md` §2) напрямую. Колонка «чем проверено нами»
регистра `l2-registers/implementation_gaps.md` пуста по всем тридцати шести строкам, и пока она
пуста, ни один шаг обоих фактов границы не подтверждён ничем, кроме документации подрядчика.
Задача закрывает эту колонку по шестнадцати строкам из тридцати шести.

## Цель
После задачи по каждому из шестнадцати шагов объёма в репо лежит проверяемый ответ на вопрос
«работает ли это на самом деле»: либо вердикт «чек / не-чек» с записанным фактом, либо дословная
причина, по которой шаг не прогонялся. Колонка «чем проверено нами» перестаёт быть пустой по этим
шестнадцати строкам, и вердикт «реализовано» впервые получает основание, отличное от заявления
подрядчика (К-1).

## Входы и факты
- **Объём — ровно шестнадцать шагов, названных поимённо** (ADR-134 §2): `OF-01`, `OF-02`, `OF-05`,
  `OF-06`, `OF-08`, `OF-11`, `OF-13`, `OF-15`, `OF-19`, `OF-20`, `OF-21`, `OF-22`, `OF-24`,
  `OF-29`, `OF-32`, `OF-36`. Перечень не пересчитывается и не переоткрывается: подстрочный отбор
  по «1С» ошибается на `OF-13`, чьё направление называет 1С отрицанием. Остальные двадцать шагов —
  задача `F4-23`, и трогать их нельзя даже походя.
- **Гейта перед задачей нет** (ADR-134 §1): `OQ-08` снят с суженной задачи, обе его открытые части
  относятся к вышедшим шагам. Формулировка ADR-104 §9 «бриф выпускается после закрытия `OQ-08`»
  относилась к несуженной задаче и стопом не служит.
- **Прогоны идут по РАБОЧЕМУ порталу Битрикса** — отдельный тестовый контур не требуется и не
  ищется: магазин не запущен, боевых данных нет (`l2-registers/open_questions.md:30`, вводная
  Owner по ADR-104 §6). Это установленный факт, а не допущение.
- **Доступность трёх внешних каналов в репо не установлена** (ADR-134 §5): Яндекс B2B Delivery API
  (`OF-20`, `OF-21`, `OF-22`), WhatsApp через Wazzup (`OF-05`, `OF-24`, `OF-29`, `OF-36`), витрина
  CMS и оформление заказа на сайте (`OF-01`, `OF-13`). Ни один шаг из-за этого из объёма не
  выброшен: «не установлено» не равно «нет» и не равно «есть» (К-14), а ни одного адреса репо,
  объявляющего канал недоступным, не существует. Доступ становится РЕЗУЛЬТАТОМ шага 1, а его
  отсутствие — записанной причиной, а не догадкой (ADR-135 §1).
- **Заявление подрядчика проверкой не является** (К-1, ADR-094 §6), пустая клетка результатом не
  является никогда (К-28). Непрогнанный шаг помечается дословно «не прогонялось, потому что …»
  (ADR-104 §2).
- **Карта — источник ожидаемого.** Расхождение прогона с картой есть НАХОДКА, а не повод править
  карту (К-2): `l0-canon/*` задачей не изменяется ни строкой.
- **Форма выхода задана и не переоткрывается** (ADR-104): семь полей на строку `OF-NN` (§2), без
  внутренних кодов проекта (§3), файл на прогон в `reference/` со ссылкой из регистра (§4),
  расщепление по стороне видно строкой (§5). Второго слоя учёта нет: вердикт живёт в колонке «чем
  проверено нами» (ADR-134 §6).
- **След номерами обязателен** (ADR-104 §7, вторая половина): прогнанный шаг оставляет номер сделки
  CRM, а где шаг ходит наружу — ещё и внешний идентификатор (`claim_id` Яндекса, идентификатор
  сообщения WA). Первая половина §7 — срок годности прогонов по боевой 1С — объёма этой задачи не
  касается: 1С в нём не участвует.
- **Внутренних кодов в протоколах нет** (ADR-104 §3): файл должен годиться и нам, и столу с
  подрядчиком. Ключи `OF-NN`, имена стадий воронки и имена событий внутренними кодами НЕ являются
  и работают. Причина «не прогонялось» пишется обычными словами: «шаг запускается ответом 1С, а
  сторона 1С в этот прогон не входит», а не ссылкой на номер решения.

## Шаги

**1. Инвентарь доступа — четыре точки, вердикт по каждой.**
Точки: (1) портал Битрикс24 — карточка сделки и REST; (2) витрина CMS и оформление заказа на
сайте; (3) WhatsApp через Wazzup — отправка шаблонных сообщений; (4) Яндекс B2B Delivery API.
По каждой пишется «доступ есть, подтверждён <чем: URL портала, ответ REST-метода, кабинет,
тестовое сообщение>» либо «доступа нет». Ответ числом: точек с установленным доступом N из 4.
Точка без доступа даёт строку открытого вопроса в `l2-registers/open_questions.md` с владельцем
Owner и становится причиной в протоколах. Догадка о доступности запрещена в обе стороны (К-14).

**2. Собрать скелет пяти протоколов ДО прогона.**
Пять полей строки из семи заполняются из карты и без всякого доступа: ключ шага · предусловие ·
действие (запрос дословно, с телом; для события — чем вызвано) · ожидаемый ответ дословно со ВСЕМИ
исходами · ожидаемые следствия (стадия сделки, резерв, запись идемпотентности, сообщение клиенту).
Это оракул: без него «чек / не-чек» не выносится, а сверять факт становится не с чем. Разбивка по
прогонам — ADR-135 §2, перечни дословно:
- `flow_run_delivery` — `OF-01`, `OF-02`, `OF-11`, `OF-19`, `OF-20`, `OF-21`, `OF-22`, `OF-29` (8)
- `flow_run_pickup` — `OF-06`, `OF-24` (2)
- `flow_run_payment_timeout` — `OF-05` (1)
- `flow_run_mutation` — `OF-08`, `OF-13`, `OF-15` (3)
- `flow_run_return` — `OF-32`, `OF-36` (2)

Сумма 8 + 2 + 1 + 3 + 2 = 16, шага без прогона нет, шага в двух прогонах первичной строкой нет.
Прогон проходит и шаги, уже получившие вердикт в другом файле (самовывоз проходит через `OF-01`):
такая строка пишется и помечается «повтор», в счёт шестнадцати не идёт и вердикт первичной строки
не отменяет — расхождение повторной строки с первичной есть находка и стоп.

**3. Установить предусловие каждой строки одним из трёх способов и записать, каким именно.**
Граница объёма проведена по полю «Направление», а триггер части шагов лежит у шага, вышедшего из
объёма (ADR-135 §3). Способы, в порядке предпочтения:
- **естественный** — предусловие создано предыдущим шагом того же прогона;
- **ручной** — стадия сделки либо стадия смарт-процесса «Возвраты» выставлена руками в карточке, и
  это записано дословно: «стадия выставлена вручную, потому что входной шаг в этот прогон не
  входит». Способ законен: роботы Битрикса срабатывают на вход в стадию, и именно их поведение
  проверяется;
- **недостижимый** — предусловие есть ответ 1С либо эквайринга и подделке не подлежит. Строка
  получает «не прогонялось, потому что …» и вердикта «чек» не получает никогда.
Ответ 1С или эквайринга не имитируется подложным вызовом ни в одном шаге: это проверило бы наш
обработчик и выдало бы результат за прогон контура.

**4. Прогнать то, что позволяет доступ, и заполнить два оставшихся поля** — «факт» (что пришло и
что изменилось на самом деле) и «вердикт» «чек / не-чек», а при не-чеке одной строкой в чём
разошлось. Поле «факт» пустым не остаётся ни в одной строке. Каждая прогнанная строка несёт номер
сделки CRM, а ходящая наружу — внешний идентификатор.

**5. Порядок безопасности прогона по боевому контуру — обязательный шаг, а не пожелание.**
Ограничения ADR-104 §7 писались под боевую 1С, и половина без 1С их первой частью не покрыта, зато
имеет собственные необратимые края: реальная заявка на доставку и реальные сообщения живому
человеку. Правила:
- клиентом всех прогонных заказов выступает НАШ номер телефона; чужой номер в прогонной сделке —
  стоп, а не мелочь;
- `OF-20` исполняется только после отдельного подтверждения Owner (класс B по правилу сомнения) и
  созданная заявка отменяется в том же прогоне, `claim_id` и факт отмены записываются. Подтверждения
  нет — строка получает «не прогонялось, потому что подтверждения на создание реальной заявки нет»;
- прогонные сделки опознаваемы: их клиентские номера заказа выписываются перечнем в служебной части
  каждого протокола, чтобы их можно было найти и исключить из любой последующей сверки.

**6. Заполнить колонку «чем проверено нами» шестнадцати строк регистра.**
Формат клетки: `<чек | не-чек | не прогонялось> · <имя файла протокола> · <дата>`. Иные колонки той
же строки не трогаются, двадцать строк вне объёма не трогаются вовсе, в том числе пробелом.

**7. Свести счёт** отдельным блоком служебной части каждого протокола плюс общим блоком в
`flow_run_delivery`: все числа §Критериев приёмки выписываются, включая нулевые.

## Критерии приёмки
- Файлов протокола в `reference/` — **5**; шагов объёма, получивших вердикт либо дословную причину, —
  **16 из 16**; шагов без того и другого — **0**.
- Ключей вне объёма в протоколах и строк регистра вне шестнадцати, изменённых задачей, — **0**.
- Пустых клеток «факт» — **0**. Строк «не прогонялось» без текста после «потому что» — **0**.
- Строк со способом предусловия из трёх названных — **все**; строк без названного способа — **0**.
  Строк, где ответ 1С или эквайринга имитировался, — **0**.
- Точек доступа с вердиктом — **4 из 4**; строк открытого вопроса заведено ровно столько, сколько
  точек без доступа.
- Прогнанных строк без номера сделки CRM — **0**; строк, ходящих наружу, без внешнего
  идентификатора — **0**.
- Прогонных сделок с чужим номером телефона — **0**. Заявок Яндекса создано N, отменено N,
  разница — **0**.
- Внутренних кодов проекта в протоколах — **0**. Проверяется дословно и вывод предъявляется
  строками (К-27, К-28):
```bash
LC_ALL=ru_RU.UTF-8 grep -nE 'ADR-[0-9]+|К-[0-9]+|CQ-[0-9]+|OQ-[0-9]+|BQ-[0-9]+|P-[0-9]+|Д9?-[0-9]+|F[0-9]-[0-9]+|Ф-[0-9]' reference/*_flow_run_*.md
```
- Строк `l0-canon/*`, `l3-external/*`, `docs/*`, изменённых задачей, — **0**.
- Вердиктов «реализовано» по шагу, который не прогонялся, — **0**: причина вердиктом не является.
- Формулы в задаче нет (К-32).

## Return-this
Пять файлов протоколов с путями и числом строк в каждом. Все числа §Критериев приёмки дословно,
включая нулевые. Вывод команды проверки внутренних кодов дословно. Инвентарь доступа четырьмя
строками. Перечень шагов с вердиктом «не-чек» — по каждому одной строкой, в чём разошлось с картой:
это и есть главный результат задачи. Перечень мест, где исполнитель испытал соблазн достроить
ожидаемое поведение или выставить вердикт без факта, и что сделал вместо этого. Плюс session-блок
по `docs/04_SESSION_PROTOCOL.md` (обязателен).

## Вне scope
- Не трогать двадцать шагов задачи `F4-23` — ни строкой протокола, ни клеткой регистра.
- Не звать 1С и не звать эквайринг ни одним вызовом, даже если доступ окажется под рукой.
- Не имитировать ответ 1С или эквайринга подложным вызовом нашего обработчика.
- Не править карту, канон и любой файл `l0-canon` (К-2): расхождение прогона с картой — находка.
- Не править снимки в `reference/` и не переписывать протокол прошлого прогона (К-33).
- Не менять вердикты и прочие колонки регистра гэпов: задача заполняет ОДНУ колонку.
- Не выносить протокол наружу и не готовить отправку подрядчику: это класс B и решение Owner.
- Не создавать заявку Яндекса без отдельного подтверждения Owner и не оставлять созданную заявку
  неотменённой.
- Не заводить второй слой учёта прогонов и не изобретать новую форму строки (ADR-134 §6).
- `git push` не выполнять.

## Эскалация
CONTEXT GAP · ожидаемое поведение не названо по адресу карты · расхождение повторной строки с
первичной · шаг требует решения о доступе, которого в репо нет · соблазн выставить вердикт без
факта либо достроить ожидание · расхождение прогона с каноном, а не с реализацией → стоп, поднять
Architect. Не решать самому.

## Дисциплины
- **★ Человеческий язык (К-16).** Правило номер один. Отчёт читает человек, а не машина: короткие предложения, обычные слова, без жаргона. Если что-то требуется от Owner — это первая строка ответа, а не последняя.
- **★ Форма ответа (К-39).** Шапка из трёх строк ПЕРВОЙ, до любого другого вывода: `Сделано:` · `Нужно от Owner:` · `Рекомендация:` — каждая одной строкой, нечего написать «нет». Дальше не более 25 непустых строк; абзац не длиннее трёх строк, перечень абзацем не считается. Коды проекта употребляются как есть, расшифровки не требуют. Хвостовых блоков после машинной части нет, блока самопроверки нет. На пути Claude Code форма проверяется машинно хуком `Stop` (`tools/hooks/answer_check.sh`): нарушение возвращает ответ на переписывание до выдачи Owner.
- **★ Упаковка смысла (К-42).** Ответ отдаёт готовый смысловой результат, а не сырьё, из которого Owner соберёт его сам. Вывод раньше доказательства; причинно-следственную связь формулируешь ты, а не читатель; последовательность собственных действий сворачивается в результат; числа выводятся только те, что меняют вывод или нужны Owner для решения. Тест перед выдачей: если после абзаца читателю надо самому сопоставлять факты и формулировать вывод, который ты уже мог сделать, — переписывай.
- **★ Разделение выхода (ADR-058, К-39 §7).** Выход делится надвое: текст к Owner и машинная часть (session-блок, FILE_PATCHES, содержимое артефакта). В машинной части коды свободны, её адресат — файл и следующая роль. На пути Claude Code машинная часть в чат НЕ печатается: её носители — файлы репо и описание коммита. На чатовом пути она печатается целиком (ADR-042 §3), потому что переносит её Owner руками.

**Скелет ответа к Owner (ADR-123 §5). Копируй форму, а не вспоминай правило:**

```
Сделано: <один результат, а не перечень действий>
Нужно от Owner: <одно решение либо «нет»>
Рекомендация: <вариант и почему, одной строкой, либо «нет»>

<Вывод.>   что получилось и что это значит
<Почему.>  причина одной-двумя фразами, связь формулируешь ты
<Детали.>  только то, без чего вывод не проверить

Развилка Р-1. <суть выбора>        ← блок только если решение нужно сейчас
  вариант А — <последствие>
  вариант Б — <последствие>
  рекомендую <вариант>, потому что <причина>
```

Слоты «Вывод / Почему / Детали» в тексте не подписываются — это порядок изложения, а не
заголовки. Строка `Развилка Р-<n>.` подписывается дословно: по ней проверка опознаёт блок и
расширяет лимит на 12 строк (К-39 §2, §6).

- **★ Anti-improvisation.** Значения/пороги/имена/схемы не выдумываются. Нет в контексте → `CONTEXT GAP` и стоп. Соблазн «дотянуть» — сигнал остановиться.
- **Доказательность (К-1).** Каждый вывод верификации — с цитатой `l3-external/md/<файл>@<SHA>:строки`. Статусы: CONFIRMED-DOC / REFUTED / NEEDS-FACT (→ черновик вопроса в Contractor Question Register; истину о поведении 1С знает только List.kg).
- **Скриптовые задачи:** ты ПИШЕШЬ код + ожидаемый вывод + команду запуска; Owner ЗАПУСКАЕТ и возвращает лог. Done — только после подтверждённого лога. Противоречивый лог = недостоверен: запроси чистый перезапуск, не примиряй половины. **Плейсхолдеров в скриптах не бывает (К-6):** каждое значение, известное из брифа, репо или сессии, подставляется литерально; значение неизвестно → `CONTEXT GAP` и стоп, а не `<...>`. Owner получает готовый к вставке скрипт, а не заготовку.
- **Не-идемпотентные операции:** обрыв → сначала read-only диагностика, потом доисполнение хвоста. Слепой retry запрещён.

## Выход
Весь выход сессии — ОДНА вставка (ADR-042 §3): return-this из брифа (дословный формат) плюс самодостаточный session-блок по `docs/04_SESSION_PROTOCOL.md`. Патчи регистров — drop-in, дословные, секцией REGISTER_PATCHES. Правки любого другого файла репо вне STATE, ADR-лога, регистров и журнала едут ВНУТРИ блока секцией FILE_PATCHES: путь, тип операции, точное место дословным якорем из текущего текста файла, дословный контент (ADR-042 §1, §4). Патч, выложенный прозой вне блока, считается невыпущенным.

### 3.1. Буфер session-блоков (источник §7.4, А5)

- Путь: `reference/_inbox/`. Заводится с заглушкой: `mkdir -p reference/_inbox &&
  touch reference/_inbox/.gitkeep`.
- **Заглушка не удаляется никогда.** Без неё каталог исчезает с диска, и проверка
  старта начинает падать по причине, к работе отношения не имеющей.
- Имя файла блока: `session_<TASK>_<YYYY-MM-DD>.md`. Файл, не подходящий под шаблон
  имени, есть гэп: остановка, а не догадка о назначении.
- Сессия кладёт свой блок ОДНИМ новым файлом и не трогает docs/00_STATE.md,
  docs/02_ADR_LOG.md, docs/02_ADR_INDEX.md, l2-registers/*. Их правит только сборка.
- **Непустой буфер есть стоп-условие старта любой другой сессии.** Пропущенная сборка
  даёт протухшее состояние, а на нём стартуют все следующие сессии.
- **Пустой буфер в основном дереве доказательством пустого буфера не является:**
  файлы лежат в неслитых ветках. Инвентаризация начинается со слияния веток.
- Правки правил (CLAUDE.md, docs/01_CONVENTIONS.md, prompts/*) под буфер НЕ подпадают:
  их сессия коммитит сама, отдельным коммитом.

**Мотив, который легко потерять:** буфер введён не для удобства, а для корректности.
При параллельных сессиях документ состояния есть единственная точка, куда пишут все.
Раньше сериализацию нёс человек. Буфер возвращает сериализацию файлом вместо человека.
Побочно определяется нумерация: правило «номер равен следующему по факту» при трёх
параллельных сессиях не определено, при сборке в один поток определено.

### 3.2. Сборщик (расширение роли Applier, не новая роль)

**Делает:** применяет накопленные блоки к STATE, ADR-логу, индексу и регистрам ОДНИМ
коммитом; раздаёт номера ADR в один поток; удаляет разобранные файлы поимённо.

**Не делает:** не решает и не адъюдицирует; не переписывает содержание блока, кроме
подстановки номера; не пишет прод-код. Механический переносчик с правом остановки,
а не архитектор с правом трактовки.

**Порядок раздачи номеров** (без него два сборщика на одном буфере дадут разный
результат):
1. по дате в имени файла, от ранней к поздней;
2. при совпадении даты по алфавиту названия задачи;
3. оговорка, перекрывающая 1 и 2: блок, ссылающийся на решение из другого блока,
   идёт после него.

Отвергнутые порядки и почему: «по времени коммита» ломается на пачке, залитой одним
коммитом; «по смыслу на усмотрение сборщика» делает сборку неперепроверяемой.

Подстановка выданного номера в текст решения, в строку индекса и во все ссылки этого
же блока есть ЕДИНСТВЕННАЯ правка содержания, которую сборщик делает.

**Определение конфликта.** Конфликт есть, если: два блока правят одну строку STATE;
один блок закрывает строку, которую другой правит; два блока дают несовместимые
формулировки одного факта; два блока претендуют на один идентификатор.

**Действие при конфликте: СТОП до первой правки.** Не применяется ни один блок,
включая бесконфликтные. Буфер остаётся нетронутым, владельцу вопрос полным блоком.
Мотив запрета частичной сборки: наполовину собранное состояние хуже несобранного,
потому что ВЫГЛЯДИТ СВЕЖИМ. Дата обновилась, половина содержимого отсутствует,
и никакой признак этого не показывает.

**Судьба SESSION_LOG.** У источника файл буфера удаляется, содержимое остаётся
в истории git. У нас SESSION_LOG уходит отдельным файлом в sessions/ (prompts/applier.md).
Наш вариант сохраняется: sessions/ у нас уже адресат.

**Сборка не кладёт свой блок в буфер** (рекурсия). Отчёт пишется в тело коммита.

**Стоп-условия сборки:** рабочее дерево грязное сверх файлов буфера; файл не подходит
под шаблон имени; блок ссылается на несуществующее и пункт помечен `[сейчас]`; пункт
блока последствий без маркера времени; конфликт по определению выше; хук дал FAIL не
по своей правке; после применения в буфере осталось что-то кроме заглушки; ветка не
сливается без конфликта; удаление ветки ключом `-d` отказывает.

### 3.3. Изоляция деревьев (источник §7.5)

```
git worktree add worktrees/<TASK> -b s/<TASK> HEAD
```

- Точка ветвления задана словом `HEAD` и умолчаний не оставляет.
- Каталог `worktrees/` в корне репо, ВИДИМЫЙ, внесён в .gitignore.
  **Почему не скрытый:** диалог выбора папки десктопного приложения скрытые каталоги
  не показывает, и первый же запуск у источника ушёл обходным путём.
- **Почему не настройка git-клиента** (`worktree.baseRef`): настройка живёт в файле
  конкретной машины и не переживает переклонирование, то есть частью метода не является.
  Инвариант держит команда или файл под версионным контролем, а не настройка машины
  и не память исполнителя.
- Дерево после сессии не удаляется и ветка не сливается сессией. И то и другое делает
  сборка: она же проверяет, что ветка слита, ключом `-d`, не `-D`. Отказ удаления есть
  стоп-условие, а не повод перейти на форсированный ключ.
- Сессия генерации брифа берёт суффикс `-GEN` для дерева, ветки и task-ID, иначе
  столкнётся за имя с сессией исполнения той же задачи.
- Исключение ровно одно и структурное: сборка идёт в ОСНОВНОМ дереве, потому что
  сливает ветки, а из связанного этого не сделать.

**Инцидент-основание (источник §7.5).** Три параллельные задачи на одном клоне сломали
три вещи сразу: одновременные правки одного документа состояния; коммиты одной сессии
подобрали застейдженные файлы другой; нумерация разъехалась. Обе стороны добавляли
файлы поимённо, и это не помогло. Ни одна из трёх поломок не лечится дисциплиной
git-команд.

### 3.4. tools/session_status.sh (источник А8, готовый скрипт, адаптировать пути)

Печатает четыре счётчика: изменённые файлы, файлы буфера кроме заглушки, рабочие
деревья, ветки `s/*`. Ненулевой код при «не чисто». Различает основное и связанное
дерево: внутри своего дерева чужие деревья и ветки нормальны и стопом не являются.

Критерий утвердительный и числом: не «вывода нет», а «файлов кроме заглушки: 0».
Голым `ls` каталога буфера пользоваться запрещено: вывод при каталоге с одной
заглушкой и при пустом одинаков.

### 3.5. tools/parallel_check.sh (источник А9, готовый скрипт)

Читает поле «Файлы на запись» из `briefs/<TASK>.md`, печатает наборы ЦЕЛИКОМ и все
пересечения. Пересечением считается равенство путей ИЛИ отношение каталог-предок.
Отдельный код возврата на «поле отсутствует или записано не списком»: это ОТКАЗ
проверки, а не разрешение.

Условие параллелимости состоит из двух частей: допуск это свойство ОДНОЙ задачи
(класс A и объявленный набор), непересечение это свойство ПАРЫ, и одна задача его
знать не может.

### 3.6. tools/method_check.sh (наша рекомендация 5, не из источника)

Считает признаки исполнения из docs/08_METHOD_PLAN.md: дней подряд со строкой
в sessions/JOURNAL.md; чисел в docs/00_STATE.md без ссылки на подтверждающий файл;
аномалий, заведённых не в день обнаружения. Печатает числа, не вердикты.

В волне 1 не помещается по существу: признак П-1 требует 14 дней журнала, а в журнале
одна строка. Скрипт, написанный раньше, измерял бы пустоту.

### 3.7. Роль Generator (источник §7.1, А4)

`prompts/generator.md`, биндинг Sonnet, строка в docs/03_ROLES.md, режим в раннбуке.

- Читает репо и выдаёт бриф следующей задачи. Задачу НЕ выполняет.
- **Первым шагом цитирует дословно «Текущий фокус» из docs/00_STATE.md и строку статуса
  релевантной задачи, ДО сборки брифа.** Это даёт владельцу поймать рассинхрон
  (устаревший SHA, не та задача) до, а не после.
- Определяет класс задачи по таблице §Мандат в STATE. Класса в таблице нет значит
  CONTEXT GAP, а не повод его назначить. Класс B без указанного решения, выдавшего
  мандат, означает, что задача не исполнима: бриф генерируется, в шапку ставится гейт.
- Не генерит бриф поверх нерешённого: есть нерешённые ADR и это задача с суждением
  значит сначала вынести их владельцу.
- Заполняет поля «Класс задачи», «Параллель», «Файлы на запись» строго по форме
  шаблона, последнее маркированным списком, оно машиночитаемо.

### 3.8. Один скрипт на шаг брифа (источник §7.3)

Дробление read-only шага на пять скриптов есть пять лишних подтверждений и прямой
вклад в привыкание нажимать «да». Объединять диагностику и действие в один скрипт
запрещено. Перед любым подтверждением на действие класса B исполнитель обязан
ОТДЕЛЬНЫМ сообщением назвать: что именно будет исполнено, на каком объекте, чем
откатывается. Владелец отличает настоящий гейт от рутинного запуска по наличию этого
сообщения, а не по виду диалога инструмента.

## 5. Обоснование порядка «сначала буфер, потом дорожки»

Считано по документированному циклу (README §Как запустить сессию + prompts/applier.md).
Одна Executor-задача сегодня: взять SHA, открыть чат исполнителя и вставить промт
с брифом, забрать блок, открыть чат Applier и вставить блок, вставить bash в терминал,
прогнать verify, забрать новый SHA. Семь касаний владельца.

| Режим | Три задачи | Касаний владельца |
|---|---|---|
| Последовательно | 3 × 7 | 21 |
| Параллельно, без буфера | 3 × 7 | 21 |
| Параллельно, буфер и сборка в чате | 3 × 3 + сборка | 13 |
| Параллельно, буфер и сборка в Claude Code | 3 запуска + сборка | 5–6 |

**Вывод:** параллель без буфера ускоряет модель и не трогает владельца. Буфер не налог
на параллель, а то, что делает параллель выгодной владельцу.

**Три механизма тихого отказа при параллели без буфера:**
1. Дрейф SHA под drop-in-патчами. Сессии стартуют на SHA X; после применения первой
   HEAD стал X'. Патч, построенный против X, либо падает громко (хорошо), либо ложится
   на файл, который сессия не видела (тихо).
2. Затирание строк STATE. Два блока описывают переход одной строки; Applier применяет
   дословно и не адъюдицирует; половина содержимого теряется, дата обновляется.
3. Разъезд перекрёстных ссылок. Номер ADR раздаётся в момент применения; части
   декомпозированной задачи ссылаются друг на друга и получают чужие номера.

**Что не параллелится никогда:** решения (две Architect-сессии по смежным вопросам
дадут два корректных и противоречащих ADR); задачи с незакрытым гейтом; класс B.

**Наборы файлов на запись, замер на текущем фронте (2026-07-29):**

| F5-02 (P-04,16,17,26,27,30) | l2-registers/problem_register.md | с F5-01 |

Единственное реальное пересечение сегодня это регистр проблем между двумя волнами
Фазы 5. Под буфером оно перестаёт быть пересечением: ни одна сессия регистр не правит,
обе кладут блоки, сборка применяет оба одним коммитом.

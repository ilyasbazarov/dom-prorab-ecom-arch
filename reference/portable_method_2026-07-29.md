# ПЕРЕНОСИМЫЙ МЕТОД · манифест docs-driven конвейера с агентами

**Версия:** 1.0 · **Дата снимка:** 2026-07-29 · **Статус:** справочный артефакт, не действующее правило
**Провенанс:** дистилляция боевого метода одного проекта на состояние коммита `4c8c42eb`. Доменная специфика (отрасль, стек, облако) вычищена полностью. Номера решений исходного проекта в тексте не приводятся: правила названы по смыслу, чтобы принимающая сторона не тянула чужую нумерацию.
**Адресат:** архитектор другого проекта, который решает, что из этого ставить себе и в каком порядке.

## 0. Как читать

Документ отвечает на три вопроса и в этом порядке:

1. **Что это.** Разделы 1-2: зачем метод существует и из чего состоит.
2. **Как устроено.** Разделы 3-8: пять слоёв, снизу вверх, с указанием, что от чего зависит.
3. **Что решать вам.** Разделы 9-12: цена, ограничения, анкета адаптации, порядок внедрения.

Приложение А несёт обезличенные шаблоны файлов. Ставится копированием, но только после того, как пройдена анкета раздела 11: шаблон, поставленный без принятых решений, даёт видимость процесса без процесса.

**Правила в этом документе почти всегда сопровождаются инцидентом, из которого родились.** Это сделано намеренно. Правило без причины первое, что адаптирующий выбрасывает как перестраховку, и получает тот же отказ у себя. Помеченные блоки `ШРАМ` читать обязательно, они дороже остального текста.

## 1. Какую проблему решает метод

Проблема одна: **ни один чат не держит весь проект.** Контекст растёт, деградирует, теряется вместе с закрытой вкладкой. Всё остальное следствие.

Три отказа, которые из этого вытекают, и три ответа метода:

| Отказ | Как выглядит | Ответ метода |
|---|---|---|
| Знание живёт в чате | Через месяц никто не помнит, почему сделано так; повторные решения расходятся с прежними | Знание живёт в плоском наборе `.md` в репозитории; чат берёт срез и умирает |
| Модель дотягивает недостающее | Правдоподобное имя, порог, схема, подставленные вместо факта; ошибка обнаруживается через недели | Anti-improvisation: нет входа значит остановка и вопрос, не догадка |
| Сессия закончилась и ничего не осталось | Работа сделана, но состояние проекта не сдвинулось | Session-блок как единственный способ пережить сессию |

Метод не про скорость сам по себе. Скорость появляется на слое 4, и только если слои 0-2 уже стоят. **Конвейер, поставленный на проект без журнала решений и единого документа состояния, разваливается на второй-третьей неделе:** сборке нечего собирать, номера решений не во что складывать, стоп-условия не защищают ничего.

## 2. Пять слоёв и порядок внедрения

```
  слой 4 · КОНВЕЙЕР        режимы запуска, мандаты, буфер, деревья, машинные проверки
     ^                     (то, ради чего обычно и приходят)
     |
  слой 3 · DISCOVERY       гэп это задача добычи знания, а не тупик
     ^
     |
  слой 2 · ДИСЦИПЛИНА      append-журнал решений + индекс, архив, blast radius
     ^
     |
  слой 1 · ГРАНИЦА         жёсткий контракт: развязывающий интерфейс либо референс-оракул
     ^                     (самое трудное решение при переносе)
     |
  слой 0 · ФУНДАМЕНТ       знание в репо, роль это не чат, anti-improvisation, session-блок
```

**Зависимости жёсткие снизу вверх и мягкие вбок.**

- Слой 0 самодостаточен. Ставится за два дня, окупается сразу.
- Слой 1 не имеет технической реализации, это решение. Без него слой 2 работает, но приёмка становится вкусовой: спор «сошлось или нет» решается авторитетом, а не цифрой.
- Слой 2 требует слоя 0. Он же обязательное условие слоя 4.
- Слой 3 требует слоёв 0 и 2. Ставится тогда, когда стало ясно, что исходное знание неполно.
- Слой 4 требует слоёв 0 и 2. Слой 3 желателен, но не обязателен.

**Слой 4 без слоя 2 ставить нельзя.** Симптом преждевременности: буфер session-блоков есть, а документа состояния, куда их применять, нет; тогда буфер превращается в свалку датированных файлов, которые никто не разбирает.

## 3. Слой 0 · Фундамент

### 3.1. Знание живёт в репозитории, а не в контексте

Плоский набор нумерованных `.md` в корне. Не база знаний, не вики, не тикет-система: обычные файлы под git, которые модель читает целиком.

Причина именно такой формы: файл под git имеет историю, диффы, атомарные коммиты и одну версию истины на коммит. Вики и тикеты этого не дают, а модель в них ходит хуже.

### 3.2. Роль это не чат

Свежий чат становится ролью, загрузив её обязательный контекст. Старые чаты ретайрятся, не живут вечно и не накапливают привилегий.

Из этого два следствия, оба неочевидные:

- **Файл-бутстрап на каждую роль.** «Один файл, одна роль». Роль описана текстом, который вставляется в начало нового чата. Смена роли значит новый чат, а не переключение внутри старого.
- **Обязательный контекст роли фиксирован документом,** а не памятью человека. Иначе через месяц одна и та же роль стартует с разным набором входов и даёт несопоставимые ответы.

### 3.3. Anti-improvisation, главный закон

Требуемый документ, вход, значение или решение отсутствует в контексте, значит роль **останавливается**:

```
CONTEXT GAP: <что именно отсутствует и почему без него нельзя продолжить>
```

и спрашивает человека. Запрещено выдумывать, дотягивать, подставлять правдоподобные пороги, имена, схемы.

Формулировка «лучше остановка, чем тихая фабрикация» звучит банально ровно до первого случая, когда фабрикация обнаружилась через три недели и потянула за собой четыре зависимых решения.

Рядом с `CONTEXT GAP` живёт вторая, отдельная метка:

> `СОДЕРЖИМОЕ НЕ ТО: <файл> — ожидалось <что>, внутри <что>`

**ШРАМ 1 (подменённый файл).** Документ с одним именем содержал копию другого документа. Запрос отдавал `HTTP 200`, файл читался, парсился, выглядел исправным. Сессия отработала на неверном входе целиком. Отказ был **тихий**, и именно поэтому он получил собственную громкую метку вместо `CONTEXT GAP`: `CONTEXT GAP` про «файла нет», здесь файл есть и врёт.
**Правило:** каждый документ проекта начинается строкой со своим именем (`# FILE: <имя>` либо `# NN · <ИМЯ>`), роль сверяет первую строку каждого загруженного файла до переформулировки задачи и до любой содержательной работы.

### 3.4. Успех инструмента не равен факту

Три правила одного класса, каждое из инцидента.

**ШРАМ 2 (пустая выдача).** `rc=0` при нулевой, пустой или непарсимой выдаче было прочитано как «данных нет». Данные были.
**Правило:** отсутствие данных в выводе не есть доказательство отсутствия данных в системе. Пока обратное не подтверждено независимым способом, это **гэп наблюдения**, а не результат.

**ШРАМ 3 (ложный вердикт поиска).** Скрипт с текстовым поиском напечатал вердикт «искомой конструкции в коде НЕТ». Конструкция была, но разнесена на несколько строк исходника, а поиск шёл построчно. Вердикт был уверенный, короткий и ложный.
**Правило:** скрипт, выносящий вердикт, обязан печатать **совпавшие строки с номерами**, а не метку `PASS`/`FAIL`. Метка непроверяема, строки проверяемы.

**ШРАМ 4 (неоднозначный критерий пустоты).** Проверка «каталог пуст» делалась через листинг каталога. Каталог с одним служебным файлом-заглушкой и каталог пустой дают одинаковый вывод. Два разных состояния читались как одно.
**Правило:** критерий формулируется **утвердительно и числом**. Не «вывода нет», а «файлов кроме заглушки: 0». Пустой вывод результатом не является никогда.

### 3.5. Session-блок

Сессия, не закрытая структурным блоком, равна потерянной. Формат ниже генерится **дословно** и применяется механически.

````md
=== SESSION LOG · <дата> · <task-id> ===

## SESSION_LOG
- Задача: <T-id> — <название>
- Сделано: <маркеры>
- Команды/логи ключевые: <кратко>
- Отклонения от плана: <если были, иначе "нет">

## STATE_PATCH   (применяется всегда)
- Задача <T-id>: <старый статус> → <новый статус>
- Текущий фокус: <что дальше>
- Новые открытые вопросы: <список или "нет">
- Блокеры: <список или "нет">
- updated_at: <дата>
- обновил: <роль> (сессия: <T-id>)

## NEW_DECISIONS   (только accepted применяется)
- РЕШЕНИЕ-NN: <заголовок>
  Контекст: <зачем>
  Решение: <что>
  Последствия: <по пункту на файл/раздел/строку, каждый с маркером времени прихода>
  Статус: accepted | proposed (требует апрува)

## NEW_CONVENTIONS   (по умолчанию proposed, без апрува не применяется)
- <предложение>

=== END SESSION ===
````

**Почему `proposed` по умолчанию:** это защита источника истины от тихого дрейфа. Роль имеет право предложить правку правил и не имеет права её внести.

**Маркеры времени прихода** в блоке последствий: `[сейчас]`, `[отдельным коммитом]`, `[задачей <ID>]`, `[без правок]`.

**ШРАМ 5 (два стопа на исправных решениях).** Два корректных решения написали в последствиях «правки идут отдельным коммитом». Механический применяющий проход прочитал это как утверждение о свершившемся факте, пошёл искать файлы в репозитории, не нашёл и остановился. Останавливаться он был обязан; неверна была формулировка, а не поведение.
**Правило:** каждый пункт последствий начинается маркером, отвечающим на вопрос «когда эта правка окажется в репо», а не «что она меняет». Пункт без маркера есть гэп, а не повод трактовать по смыслу.

## 4. Слой 1 · Граница контракта

**Это самое трудное решение при переносе, и оно не техническое.**

Метод держится на существовании красной линии, которую слои не пересекают. Линия бывает в двух формах, проект может опираться на одну или обе.

### (а) Развязывающий интерфейс

Жёсткий артефакт или схема между слоями. Всё выше (как он строится) и всё ниже (что из него строится) независимы. Производителя можно заменить, не трогая потребителя.

Это причина, по которой проект **фазируется без переписывания**: можно поменять источник данных, не переделывая витрины, если контракт между ними зафиксирован документом.

### (б) Референс-оракул приёмки

Внешний источник истины, с которым выход проекта обязан биться **по цифрам**. Расхождение закрывается правилом, override-ом или зафиксированным решением, но **никогда тихим примирением** «более правдоподобной» половины.

В исходном проекте оракулом был внешний интерфейс учётной системы: то, что видит клиент на экране. Иерархия источников эталона была прописана явно, по убыванию доверия, вплоть до «ручная копия страницы, датированный снимок в каталог эталонов».

### Закон-следствие

**Слой не лезет через границу чинить чужой слой.** Дефект правится фикс-форвардом в тот слой, где причина. Мерить там, где видно; чинить там, где причина.

Формулировка выглядит очевидной и нарушается постоянно: в нижнем слое чинить дешевле и быстрее, потому что доступ уже есть.

### Что делать, если у вас нет ни того, ни другого

Честный ответ: **метод всё равно даст дисциплину, но не даст приёмки.** Вы получите порядок в решениях и состоянии, но спор «сделано правильно или нет» будет решаться авторитетом.

Три ходовых заменителя, по убыванию силы:

1. **Ручной эталон, зафиксированный один раз.** Датированный снимок эталонных значений в каталог `/reference`, с указанием, откуда взят и на какой момент. Слабее живого оракула, но проверяем.
2. **Приёмочный набор кейсов.** Список проверяемых утверждений с ожидаемым результатом, зафиксированный до реализации, а не после.
3. **Внешний потребитель как арбитр.** Тот, кто увидит расхождение раньше вас, назначается источником истины формально.

Если ни один из трёх не годится, зафиксируйте это письменно в конституции проекта как известное ограничение. Незафиксированное отсутствие границы позже читается как её наличие.

## 5. Слой 2 · Дисциплина решений и состояния

### 5.1. Таксономия документов

Плоский нумерованный набор в корне. Колонка «изменчивость» не украшение: она определяет, кто и как имеет право править файл.

| Документ | Роль | Изменчивость |
|---|---|---|
| `00_CHARTER` | конституция: миссия, **граница контракта**, scope in/out, критерии успеха, карта документов | STABLE |
| `01_ARCHITECTURE` | топология, последовательность прогона | STABLE |
| `02_*_CONTRACTS` | схемы граничных артефактов | STABLE |
| `03_*_SPEC` | доменная логика ядра | SEMI-STABLE |
| `04_ROADMAP` | эпики, задачи с ID, критерии приёмки | LIVING |
| `05_CONVENTIONS` | нейминг, код-стандарт, **правила агента, протокол сессий** | SEMI-STABLE |
| `06_DECISIONS_LOG` | журнал решений, **append-only** | LIVING (append) |
| `06_INDEX` | индекс решений: номер, заголовок, статус | LIVING |
| `07_STATE` | текущее состояние, открытые вопросы, текущий фокус | LIVING (каждая сессия) |
| `07_ARCHIVE` | архив закрытых строк состояния | LIVING (append) |
| `08_TASK_BRIEF_TEMPLATE` | шаблон пакета-передачи исполнителю | STABLE |
| `09_RUNBOOK` | как запускать сессии, для владельца | LIVING |
| `09_GLOSSARY` | доменные термины | SEMI-STABLE |
| `10_*_PLAYBOOK` | грабли по типам операций | LIVING |
| `11_*_FACTS` | волатильные инфра-факты: ID, ревизии, расписания | LIVING |
| `/reference` | эталонные выгрузки и снимки | append |

Каркас ролей отдельно: `_METHOD.md`, `_ARCHITECT.md`, `_GENERATOR.md`, `_ASSEMBLER.md`, `CLAUDE.md`, `briefs/<TASK>.md`.

**Правило дорожной карты:** детально расписан ТОЛЬКО текущий эпик. Будущие эпики это заголовок и scope, без выдуманных задач. Расписанный на полгода вперёд роадмап есть нарушение anti-improvisation, просто отложенное.

**Инвариант-минимум контекста для любого рабочего чата:** конституция + конвенции + состояние + конкретный бриф. Остальное по списку в брифе.

### 5.2. Три правила журнала решений

**Append-only.** Прошлые решения не редактируются никогда. Новое решение это новая запись, помечающая старую `superseded` либо `superseded-in-part`. Ретро-правка журнала лишает смысла весь журнал: если запись могла измениться задним числом, ссылаться на неё нельзя.

**Индекс синхронен журналу тем же коммитом.** Каждая запись в журнале даёт строку в индексе. Причина прагматичная: журнал растёт до сотен килобайт и в обязательный контекст роли не помещается, роль читает индекс, а полный текст поднимает точечно по номеру. Синхронность проверяется механически, см. раздел 7.6.

**Blast radius перечисляется полностью.** Решение, двигающее значение, перечисляет ВСЕ затронутые места в формате файл, раздел, строка. Иначе применяющий проход достраивает список догадками.

**ШРАМ 6 (остаток после правки по якорям).** Решение отменило требование, действовавшее в шести местах, и перечислило четыре. Два остатка нашлись случайно, через две сессии, попутно другой работой.
**Правило:** решение, **отменяющее или переопределяющее понятие** (а не двигающее значение), применяется не только по перечисленным якорям. Исполнитель обязан прогнать сплошной поиск понятия по репозиторию, напечатать совпавшие строки с номерами и внести в блок последствий решение по КАЖДОМУ совпадению: «правится» либо «остаётся, потому что». Пустая выдача поиска фактом не является, см. ШРАМ 3.

### 5.3. Документ состояния и архив

`07_STATE` держит **только открытое**: в работе, отложено, ожидает решения. Полностью закрытая строка переезжает дословно в `07_ARCHIVE` тем же коммитом, что и закрывающий её патч.

Причина не эстетическая. Документ состояния читает каждая роль на старте каждой сессии. Он растёт быстрее всех прочих, и через два месяца обязательный контекст перестаёт помещаться. Компактность горячего контекста это ресурсное ограничение, а не гигиена.

Реестр гэпов живёт там же, в разделе «Открытые вопросы». Закрытие гэпа значит решение или референс-артефакт, но не молчаливое удаление строки.

### 5.4. Идентификаторы и датировка

**Идентификаторы только латиницей.** Проверка на кириллические гомоглифы (`М С Е А Р О Т Н К В Х`) внутри префиксов идентификаторов.

**ШРАМ 7 (гомоглиф в идентификаторе).** Механический применяющий проход адресует строки документа состояния буквальным текстовым поиском по идентификатору. Кириллическая `С` внутри латинского идентификатора даёт ноль совпадений либо совпадение не с той строкой. Отказ тихий.
**Правило:** проверка scoped **только на идентификаторы**, намеренно. Обычные латинско-кириллические композиты проекта (`GAP-реестр`, `session-блок`) легитимны, и правило, срабатывающее на них, будет отключено за одну сессию.

**Датировка расщеплена на две роли.** Имена сессий и артефактов датируются локальной датой (канон проекта). Любой временной ФАКТ в тексте пишется в UTC с явным суффиксом `Z`.

**ШРАМ 8 (смешение дат).** Смешение «как называется сессия» и «что зафиксировано как факт» дало уверенный ложный вывод о пропущенном прогоне. Прогон был, разошлись часовые пояса.

### 5.5. Критерий приёмки выводится из формулы, а не из свойства данных

**ШРАМ 9 (невыполнимая приёмка).** Критерий гласил: «после правки величина не изменится», и выводился из наблюдения над входными данными («за месяц одно значение параметра»). Прежняя формула брала параметр на дату пересборки, новая на дату операции. Сдвиг был арифметически неизбежен. Приёмка оказалась невыполнимой **по построению**, и это выяснилось на прогоне, а не на формулировке.
**Правило:** формулируя приёмку правки формулы, выпишите обе формулы и предъявите разницу ДО прогона. Ненулевая разница входит в приёмку как ожидаемая величина, а не как условие «не изменилось».

## 6. Слой 3 · Discovery-петля

Расширение поверх базового метода. Нужно проектам, где **исходное знание заведомо неполно** и гэпы это норма, а не исключение. Без петли команда либо встаёт на каждом гэпе, либо начинает гадать.

Цикл из пяти шагов:

1. **DETECT.** Любая роль ловит `CONTEXT GAP`.
2. **CLASSIFY.** Архитектор квалифицирует: блокер или нет; тип (недостающий факт / нерешённое решение / отсутствующий референс-артефакт).
3. **DISCOVER.** Ставится **discovery-бриф**: задача добычи знания. Замер, расследование, ручная выгрузка из внешнего источника, интервью с владельцем.
4. **CAPTURE.** Находка обогащает репозиторий: новое решение, референс-артефакт, патч документа. Не в чат, в репо.
5. **RESUME.** Исходная задача разблокирована подтверждённым фактом.

**Правила петли:**

- Гэп не дотягивается догадкой. Он либо закрыт дискавери, либо явно отложен с фиксацией в документе состояния.
- Discovery-бриф это обычный бриф, но его «что вернуть» есть обогащение репозитория, а не прод-код.
- Внешне добытые эталонные значения фиксируются как референс-оракул: последующая приёмка бьётся об них.

**Практическая ценность петли выше ожидаемой.** Она превращает «мы не знаем» из блокера в задачу с оценкой. На проекте с неполным источником это половина всей работы, и без петли эта половина выглядит как простой.

## 7. Слой 4 · Конвейер автоисполнения

Здесь появляется скорость. Всё предыдущее было условием.

### 7.1. Роли-бутстрапы

| Роль | Файл | Делает | Не делает |
|---|---|---|---|
| **Архитектор** | `_ARCHITECT.md` | проектирует, принимает решения, правит документацию, держит целостность, ставит discovery-задачи | не пишет прод-код задач, не применяет `proposed` молча |
| **Генератор** | `_GENERATOR.md` | читает репо и выдаёт бриф следующей задачи | не выполняет задачу |
| **Исполнитель** | `CLAUDE.md` + бриф | берёт ОДИН бриф, делает работу, коммитит в свою ветку | не правит журнал решений, индекс и состояние |
| **Сборщик** | `_ASSEMBLER.md` | разбирает буфер session-блоков, применяет одним коммитом, раздаёт номера решений | не решает, не адъюдицирует, не апрувит `proposed` |
| **Владелец** | человек | владеет решениями, подтверждает необратимое, пушит | — |

Подмножество ролей допустимо. Минимальный работающий набор: архитектор, исполнитель, владелец. Генератор и сборщик добавляются, когда задач стало больше одной в день.

**Ключевая мысль про генератор:** брифы НЕ пишутся в одном вечном архитекторском чате. Бриф это repo-driven задача: свежий чат читает репозиторий и выдаёт бриф. Это и есть механизм масштабирования без тяжёлых чатов. Механический бриф (задача расписана в роадмапе) идёт дешёвой моделью, бриф с суждением идёт архитектором, который сначала закрывает открытые решения.

### 7.2. Пять режимов запуска

Отдельный документ для **владельца**, а не для сессии. Отвечает на один вопрос: что нажать и что написать.

| Что нужно | Режим | Где |
|---|---|---|
| Обсудить, принять решение, разобрать проблему, ревью | **Ч** архитектор | обычный чат либо инструмент |
| Сделать бриф следующей задачи | **Г** генератор | инструмент, своё дерево, имя с суффиксом `-GEN` |
| Выполнить одну готовую задачу | **И** исполнитель | инструмент, своё дерево |
| Выполнить несколько задач сразу | **П** параллель | инструмент, дерево на задачу |
| Разобрать накопленные session-блоки | **С** сборка | инструмент, ОСНОВНОЕ дерево |

**Правило очерёдности:** есть что-то в буфере либо есть неслитые ветки сессий, значит сначала режим С, потом всё остальное.

**Почему этот документ обязателен.** Требование владельца в исходном проекте звучало так: ссылки на роли и документы руками не прикладываются. Внутри инструмента файл законов подхватывается сам, остальное сессия читает с диска по нему. Прикладывать ссылки нужно только в обычном чате, у которого нет доступа к диску. Без раннбука владелец каждый раз пересобирает пусковое сообщение заново и каждый раз по-разному.

Тексты первых сообщений лежат в раннбуке готовыми, копируются целиком, подставляется только имя задачи.

### 7.3. Мандаты: классы задач

Мандат выдаётся **по классу задачи, а не по задаче**. Иначе каждая задача требует отдельного решения, и конвейер встаёт.

**Класс A** идёт постоянно, нового решения не требует: чтение репозитория и внешних систем; запись только в изолированные (staging) области и в каталог эталонов; коммит в локальный репозиторий. Публикация наружу остаётся на подтверждении.

**Класс B** требует задача-специфичного решения: правка живых конфигураций, деплой, доступ к секретам, любые операции над деньгами и над поверхностями, которые видит внешний потребитель.

**При сомнении задача идёт в класс B.** Обоснование арифметическое: ошибка в сторону B стоит одной архитекторской сессии, ошибка в сторону A стоит инцидента на живом проде.

**Класс объявлен в трёх местах:** поле в шапке брифа, таблица в документе состояния, файл законов. **Расхождение между брифом и состоянием есть стоп-условие сессии**, а не повод выбрать удобный класс.

Рабочие файлы сессии (скрипты, логи, промежуточные дампы) пишутся в отдельный датированный каталог с самого начала, не в корень репозитория, и коммитятся вместе с артефактом как провенанс.

**Промежуточная мера про подтверждения.** Один скрипт на ШАГ брифа, а не на команду: дробление read-only шага на пять скриптов есть пять лишних подтверждений и прямой вклад в привыкание нажимать «да». При этом объединять диагностику и действие в один скрипт запрещено. Перед любым подтверждением на действие класса B исполнитель обязан **отдельным сообщением** назвать: что именно будет исполнено, на каком объекте, чем откатывается. Владелец отличает настоящий гейт от рутинного запуска по наличию этого сообщения, а не по виду диалога инструмента.

### 7.4. Буфер session-блоков и проход сборки

**Механика.** Сессия не применяет свой session-блок сама. Она кладёт блок целиком одним НОВЫМ файлом `reference/_inbox/session_<TASK>_<YYYY-MM-DD>.md` и не трогает документ состояния, журнал решений и индекс. Отдельный проход сборки разбирает буфер, применяет накопленные блоки **одним коммитом**, присваивает номера решений по порядку и очищает буфер.

**Мотив не удобство, а корректность.** При параллельных сессиях документ состояния есть единственная точка, куда обязаны писать все. Раньше сериализацию этой записи нёс человек. Буфер возвращает сериализацию файлом вместо человека. Побочно решается нумерация: правило «номер равен следующему по факту» при трёх параллельных сессиях неопределено, при сборке в один поток определено.

**Порядок раздачи номеров** (иначе два разных сборщика на одном буфере дадут разный результат):

1. по дате в имени файла, от ранней к поздней;
2. при совпадении даты по алфавиту названия задачи;
3. оговорка, перекрывающая пункты 1 и 2: блок, ссылающийся на решение из другого блока, идёт после него.

Порядок «по времени коммита» отвергнут: ломается на пачке, залитой одним коммитом. Порядок «по смыслу на усмотрение сборщика» отвергнут: сборку тогда нельзя перепроверить.

Подстановка фактически выданного номера в текст решения, в строку индекса и во все ссылки этого же блока есть **единственная правка содержания, которую сборщик делает.** Всё остальное переносится дословно.

**Конфликт между блоками.** Конфликт есть, если два блока правят одну строку состояния; один блок закрывает строку, которую другой правит; два блока дают несовместимые формулировки одного факта; два блока претендуют на один идентификатор.

**Действие: СТОП до первой правки.** Не применяется ни один блок, включая бесконфликтные. Буфер остаётся нетронутым, владельцу задаётся вопрос полным блоком.

**ШРАМ 10 (частичная сборка).** Мотив запрета частичной сборки: наполовину собранный документ состояния хуже несобранного, потому что **выглядит свежим**. Дата обновилась, половина содержимого отсутствует, и никакой признак этого не показывает. Тихий отказ в этом методе есть худший класс отказа.

**Непустой буфер есть стоп-условие старта любой другой сессии.** Пропущенная сборка даёт протухшее состояние, а на протухшем состоянии стартуют все следующие сессии.

**Неодобренное.** Предложение со статусом `proposed` сборщик не применяет и не апрувит. Формулировка переносится строкой в открытые вопросы с указанием, из какого блока пришла, а файл буфера удаляется на общих основаниях. Оставить файл в буфере до апрува нельзя: непустой буфер блокирует старт следующей сессии, и одно неодобренное предложение остановило бы весь конвейер.

**Судьба журнала сессии.** Файл буфера удаляется, но содержимое остаётся в истории git: сессия закоммитила этот файл своим коммитом. Восстановить ход сессии, не оставившей решений, можно через историю добавлений в каталог буфера. Отдельный постоянный адресат под журналы не заводится: каталог копится, а читают его редко и обычно в ходе расследования, которое всё равно идёт по коммитам.

**Сборка не кладёт свой session-блок в буфер:** это дало бы рекурсию. Свой отчёт она пишет в тело коммита.

### 7.5. Изоляция сессий: дерево и ветка

**Одна сессия, одно рабочее дерево, одна ветка.**

**ШРАМ 11 (две сессии на одном дереве).** Владелец запустил три параллельные задачи на одном локальном клоне. Сломались три вещи сразу: сессии одновременно генерили правки в один и тот же документ состояния; коммиты одной сессии подбирали застейдженные файлы другой; нумерация решений разъехалась. **Обе стороны инцидента добавляли файлы поимённо, и это не помогло.** Ни одна из трёх поломок не лечится дисциплиной git-команд.

Дерево заводится **явной командой, а не флагом инструмента**:

```
git worktree add worktrees/<TASK> -b s/<TASK> HEAD
```

Точка ветвления задана словом `HEAD` и умолчаний не оставляет.

**ШРАМ 12 (настройка вместо метода).** Первая версия правила опиралась на настройку git-клиента (`worktree.baseRef`). Настройка живёт в файле конкретной машины и не переживает переклонирование, то есть частью метода не является. Тот же дефект был у попытки держать исключения в локальном файле игнорирования вместо `.gitignore`.
**Правило:** инвариант держит команда или файл под версионным контролем, а не настройка машины и не память исполнителя.

**ШРАМ 13 (скрытый каталог).** Деревья сначала клали в скрытый каталог. Диалог выбора папки десктопного приложения скрытые каталоги не показывает, и первый же запуск ушёл обходным путём. Каталог переехал в видимый `worktrees/` в корне репозитория, оба пути внесены в `.gitignore`.

**Что даёт git бесплатно:** ветка одна на сессию, потому что git физически не даёт выложить одну ветку в два дерева. Инвариант держит инструмент.

**Исключение ровно одно и оно структурное:** проход сборки идёт в ОСНОВНОМ дереве, потому что сливает ветки в основную, а из связанного дерева этого не сделать.

**Сессия генерации брифа берёт имя с суффиксом `-GEN`** для дерева, ветки и task-ID: иначе она столкнулась бы за имя с сессией исполнения той же задачи.

**Дерево после сессии не удаляется и ветка не сливается сессией.** И то и другое делает проход сборки: он же проверяет, что ветка действительно слита (ключ `-d`, не `-D`; отказ удаления есть стоп-условие, а не повод перейти на форсированное удаление).

**Пустой буфер в основном дереве доказательством пустого буфера не является:** файлы сессий лежат в неслитых ветках. Инвентаризация начинается со слияния веток.

### 7.6. Три машинные проверки

Правило, которое проверяет человек, соблюдается примерно до третьей недели. Ниже минимальный набор, который проверяет машина.

**(1) Состояние старта одной командой** (`tools/session_status.sh`). Печатает четыре счётчика: изменённые файлы, файлы буфера кроме заглушки, рабочие деревья, ветки сессий. Возвращает ненулевой код при «не чисто». Различает основное дерево и связанное: внутри своего дерева чужие деревья и ветки нормальны и стопом не являются.

**(2) Проверка пары задач на параллелимость** (`tools/parallel_check.sh`). Условие параллелимости состоит из двух частей, и вторая проверяется машиной:

- **Допуск** это свойство ОДНОЙ задачи: класс A и полный набор файлов на запись объявлен в брифе. Класс B не параллелится никогда.
- **Непересечение наборов** это свойство ПАРЫ задач, и одна задача его знать не может.

Скрипт читает поле «Файлы на запись» из брифов, печатает наборы целиком и все пересечения. Отдельный код возврата на случай «поле отсутствует или записано не списком»: это **отказ проверки, а не разрешение**.

Живой пример: две задачи обе несут допуск `да`, но обе пишут в один документ. По отдельности каждая параллелима, вместе нет. Проверка это печатает.

**(3) Pre-commit хук.** Пять механических инвариантов: первая строка документа равна его имени; кириллица внутри идентификаторов; новая запись в журнале решений требует строки в индексе тем же коммитом; строка, исчезнувшая из состояния, требует архива тем же коммитом; правка состояния требует обновления даты.

**ШРАМ 14 (нестабильный хук).** Один и тот же набор изменений давал разные исходы: тихий незакоммит, ненулевой код без вывода, ложное срабатывание, обрыв по сигналу трижды подряд. Две причины, обе класса «проверка сломана незаметно»: пайп в утилиту, читающую первые строки, давал сигнал обрыва на файлах больше буфера пайпа; класс символов, заданный через скобочное выражение, под байтовой семантикой локали распадался на множество БАЙТОВ, и ведущий байт совпадал с любой кириллицей.
**Правило:** **сломанная проверка хуже отсутствующей, потому что отказ тихий.** Хук сопровождается самотестом, самотест прогоняется ДО первого коммита сессии, любой провал есть остановка и вопрос владельцу.

**ШРАМ 15 (замер по синтетике).** Три инцидента подряд одного класса: заявка «проверка замерена» опиралась на вход, не встречающийся в репозитории. Синтетическая фикстура доказывает, что проверка умеет краснеть, и не доказывает, что она не краснеет на легитимном входе.
**Правило:** замер, обосновывающий механическую проверку, идёт по РЕАЛЬНОМУ содержимому репозитория.

**Про ложные срабатывания.** Хук изначально ловил любую переформулировку строки состояния как «строка исчезла» и требовал архива. Это был документированный ложный позитив, вынуждавший обходить хук на каждой правке. Обход вошёл в привычку раньше, чем правило было исправлено. Вывод: **ложный позитив в механической проверке дороже отсутствия проверки**, потому что обучает обходу.

### 7.7. Права инструмента

Список прав в конфигурации инструмента делится на три части:

- **allow**: всё read-only. Чтение, поиск, статус, диффы, логи, describe, list, локальный коммит.
- **ask**: всё, что меняет внешний мир либо публикует. Деплой, апдейт, удаление, публикация наружу, доступ к секретам, запись в живые системы.
- **deny**: разрушительное и не нужное никогда. Форсированная публикация, жёсткий сброс, перебазирование, рекурсивное удаление.

**Про трение.** Удаление файлов из буфера сборщиком не внесено ни в один список, то есть на каждое удаление инструмент запрашивает подтверждение. **Это норма, а не сбой.** Удаление есть ровно тот случай, где подтверждение несёт защитную функцию, в отличие от read-only шагов.

Правка списка прав есть изменение решения и требует отдельного решения, а не правки на месте.

## 8. Слой 5 · Язык общения с владельцем

Сквозной слой. Технически не обязателен, практически решает, будет метод жить или нет.

Шесть правил:

1. **Проза к владельцу читается без открывания репозитория.** Внутренние идентификаторы это язык session-блоков, патчей и документов. В прозе к владельцу идентификатор допустим только с расшифровкой смысла в той же фразе, и только если без него нельзя.
2. **Два слоя в каждом ответе:** «для владельца» обычными словами и «для репо» патчами. Не смешивать.
3. **Рассуждение без вывода не выдаётся.** Каждый блок к владельцу кончается действием, развилкой или явным «действий не требуется».
4. **Вопрос владельцу только полным блоком:** что решаем обычными словами, варианты, плюсы, минусы и риски, рекомендация с обоснованием. То же для любых предупреждений.
5. **Вопрос, который роль может снять своей работой, владельцу не задаётся.** Сначала снимается: замером, чтением репозитория, командой, которую владелец и так запускает.
6. **Сначала ответ, потом обоснование.**

Отдельно про форму выдачи: **владельцу отдаются готовые артефакты, а не пошаговые инструкции в духе «найди, додумай, вставь».**

**ШРАМ 16 (копипаст).** Блок команд был вставлен не в ту оболочку, часть текста сообщений об ошибках исполнилась как команды. Разрушительного не произошло по случайности.
**Правило:** команды копипаст-безопасны (в интерактивной строке комментарий после решётки может исполниться), многошаговая диагностика идёт скриптом-файлом с логом в файл, а не россыпью интерактивных вызовов. Первой и последней командой скрипта идёт фиксация времени и состояния авторизации: деградация посреди прогона должна быть детектируемой.

## 9. Цена метода и когда он не нужен

Честный счёт.

**Что метод стоит:**

- Первые две недели медленнее, чем без него. Окупаемость начинается там, где проект перестаёт помещаться в голову.
- Владелец обязан быть доступен для развилок. Метод построен на том, что решения принимает человек, и упирается в его пропускную способность. Это узкое место переносится, но не устраняется.
- Дисциплина коммитов и документации требует реального времени: сборка буфера это отдельная сессия, а не фоновое действие.
- Правила накапливаются. Через полгода файл конвенций читается двадцать минут. Компактность горячего контекста приходится защищать отдельными усилиями (архив, индекс вместо полного журнала).

**Когда метод не нужен:**

- Проект помещается в одну голову и закончится через две недели.
- Нет ничего необратимого: любое действие откатывается за минуту, цена ошибки близка к нулю.
- Один исполнитель, одна сессия в неделю. Буфер и деревья тогда чистые накладные расходы.

**Минимальная разумная конфигурация,** если полный метод избыточен: конституция, конвенции, документ состояния, session-блок, anti-improvisation. Пять сущностей, ставятся за день, дают восемьдесят процентов пользы от дисциплины и ноль от конвейера.

## 10. Что в оригинале не проверено

Раздел обязателен к прочтению: без него принимающая сторона скопирует незрелое как готовое.

На состояние снимка:

1. **Параллельный запуск проверен на уровне git, но не на уровне приложения.** Замером подтверждено: индексы деревьев независимы, добавление файлов в одном дереве не видно в другом, хук из связанного дерева срабатывает. Не подтверждено наблюдением: поведение десктопного приложения при нескольких одновременных сессиях в разных папках. До закрытия этого остатка задачи шли по одной.
2. **Механизм выбора роли через встроенных агентов инструмента описан, но не проверен.** Работающий способ это текст первого сообщения из раннбука.
3. **Ограничение прав класса A на отдельную личность не реализовано.** Действует промежуточная мера про один скрипт на шаг брифа. Направление решено, переход гейтится замером с тремя неизвестными.
4. **Канон метода и файл конвенций расходятся** по одному правилу (маркеры времени прихода). Расхождение зарегистрировано открытым вопросом намеренно: канон доменно-нейтрален, его blast radius выходит за пределы одного проекта, правка owner-gated. Это пример того, как метод обходится с собственными несоответствиями: фиксирует, а не замазывает.
5. **Скрипт правки документов однажды отработал дважды,** хотя защита от повторного применения должна была остановить второй прогон. Содержимое проверено счётчиками, дублирования нет, причина расхождения не установлена. Строка в состоянии по этому поводу не заводилась, и это тоже честный факт о дисциплине.

## А1. `_METHOD.md` (канон, доменно-нейтральный)

````md
# _METHOD — Docs-driven multi-agent метод

**Версия:** 1.0 · **Статус:** STABLE
**Что это:** операционная система для ведения проекта силами моделей-агентов и человека, где знание
живёт в плоском наборе `.md`, а не в контексте чата.

## 1. Философия

- Ни один чат не держит весь проект. Знание выносится в репозиторий, чаты берут нужный срез.
- Роль это не чат. Свежий чат становится ролью, загрузив обязательный контекст. Старые чаты ретайрятся.
- Знание переживает сессию, только если зафиксировано структурным блоком и закоммичено.
- Лучше остановка, чем тихая фабрикация.

## 2. Роли

| Роль | Делает | Не делает | Обязательный контекст |
|---|---|---|---|
| Архитектор | проектирует, решает, правит доки, держит целостность | не пишет прод-код, не коммитит | 00+04+06_INDEX+07 |
| Генератор | читает репо, выдаёт бриф следующей задачи | не выполняет задачу | 00+04+05+06_INDEX+07+08 |
| Исполнитель | берёт ОДИН бриф, делает работу | не правит 06, 06_INDEX, 07 | 00+05+07+бриф |
| Сборщик | разбирает буфер, применяет одним коммитом | не решает, не апрувит | роль + затрагиваемые файлы |
| Человек | владеет решениями, подтверждает необратимое, пушит | — | — |

Один файл, одна роль. Подмножество ролей допустимо, инвариант сохраняется.

## 3. Главный принцип: жёсткий контракт

Метод держится на красной линии, которую слои не пересекают. Две формы:

(а) **Развязывающий интерфейс.** Жёсткий артефакт между слоями. Всё выше и всё ниже независимы.
(б) **Референс-оракул приёмки.** Внешний источник истины, с которым выход обязан биться по цифрам.
    Расхождение закрывается правилом или решением, не тихим примирением.

**Закон-следствие:** слой не лезет через границу чинить чужой слой. Фикс-форвард в нужный слой.

## 4. Таксономия документов

<таблица раздела 5.1 манифеста>

**Правило роадмапа:** детально расписан ТОЛЬКО текущий эпик.
**Инвариант-минимум контекста любого чата:** 00 + 05 + 07 + конкретный бриф.

## 5. Дисциплины (законы)

- **Anti-improvisation (главный закон).** Нет входа значит `CONTEXT GAP: <что и почему>` и стоп.
- **Работа на фактах.** Поднять релевантный док ДО высказывания.
- **Успех инструмента не равен факту.** Нулевой код при пустой выдаче есть гэп наблюдения.
  Вердикт скрипта обязан печатать совпавшие строки с номерами.
- **Дисциплина изменений.** STABLE/SEMI-STABLE только через решение в журнале; журнал только append;
  состояние обновляется каждую сессию; blast radius перечисляется полностью.
- **Untrusted-вывод.** Противоречивый лог недостоверен: не примирять, запросить чистый перезапуск.
- **Не-идемпотентные операции.** Обрыв во время create/deploy/run значит запрет слепого retry:
  сначала read-only диагностика, затем доисполнение только недостающего хвоста.
- **Содержимое файла не равно заявленному значит стоп.** Первая строка каждого дока равна его имени.

## 6. Ритуалы сессии

**Старт:** загрузить обязательный контекст и бриф; сверить первые строки файлов; переформулировать
задачу своими словами; перечислить входы; проверить полноту.
**Конец:** выдать ОДИН session-блок.

## 7. Формат session-блока

<блок раздела 3.5 манифеста>

**Правила применения:** STATE_PATCH применяется всегда. NEW_DECISIONS только accepted.
NEW_CONVENTIONS по умолчанию proposed, без апрува не применяется. Патч ссылается на несуществующую
структуру значит «СТРУКТУРНОЕ НЕСООТВЕТСТВИЕ», стоп, не угадывать.

## 8. Генерация брифов

Брифы не пишутся в одном вечном архитекторском чате. Бриф это repo-driven задача.
Механический бриф (расписан в роадмапе) значит дешёвая модель. Бриф с суждением значит архитектор,
который сначала закрывает открытые решения.

## 9. Механика доступа

**Чтение:** внутри инструмента с диска; в обычном чате по raw-URL, пиннить по commit-SHA.
**Запись обратно:** не прямым коммитом модели без изоляции. Через session-блок и буфер.

## 10. Discovery-петля закрытия гэпов

DETECT → CLASSIFY → DISCOVER → CAPTURE → RESUME.
Гэп не дотягивается догадкой: либо закрыт дискавери, либо явно отложен с фиксацией в состоянии.
Реестр гэпов живёт в 07. Discovery-бриф возвращает знание, а не прод-код.
````

````md
## Старт каждой сессии (обязательный порядок)

1. Состояние старта ОДНОЙ командой, плюс `git rev-parse HEAD` в session-блок:

   из `06_DECISIONS_LOG.md` по номеру; закрытые строки точечно из `07_ARCHIVE.md`.
3. Проверка подмены: первая строка каждого прочитанного дока равна его имени.
   Не совпало значит `СОДЕРЖИМОЕ НЕ ТО: <файл> — ожидалось <что>, внутри <что>` и стоп.
4. Переформулируй задачу своими словами, перечисли входы, проверь полноту.
5. Хук установлен и РАБОТАЕТ:
   `test -x .git/hooks/pre-commit || ln -s ../../tools/hooks/pre-commit .git/hooks/pre-commit`
   затем `bash tools/hooks/selftest.sh`, ожидание «провалено 0». Любой ПРОВАЛ значит стоп и
   вопрос владельцу: сломанная проверка хуже отсутствующей, потому что отказ тихий.
   До первого коммита, не после.

## Законы (нарушение любого есть провал сессии)

- **Anti-improvisation.** Нет дока/значения/решения значит `CONTEXT GAP: <что и почему>` и вопрос.
  Гэп значит discovery-петля, не догадка.
- **Работа на фактах.** Подними релевантный файл ДО высказывания.
- **Успех инструмента не равен факту.** Нулевой код при пустой выдаче есть гэп наблюдения.
  Вердикт поиска обязан печатать совпавшие строки с номерами, не метку.
- **Untrusted-вывод.** Противоречивый лог недостоверен: не примиряй половины, перезапусти чисто.
- **Не-идемпотентные операции только через явное подтверждение владельца.** Обрыв значит запрет
  слепого retry: сначала read-only диагностика, затем хвост. Диагностику и действие в один скрипт
  не объединять.
- **Граница контракта.** <ваша формулировка>. Слой не лезет через границу чинить чужой слой.
- **Исполнение внешних команд** скриптом-файлом с логом в файл, не россыпью интерактивных вызовов.
  Фиксация времени и состояния авторизации первой И последней командой скрипта.

## Дисциплина документации

- STABLE/SEMI-STABLE доки менять ТОЛЬКО через решение в журнале.
- `06_DECISIONS_LOG.md` только append. Каждый append есть строка в `06_INDEX.md` ТЕМ ЖЕ коммитом.
- `07_STATE.md` только открытое. Полное закрытие строки есть перенос дословно в `07_ARCHIVE.md`
  тем же коммитом. Дата и подпись обновляются каждую сессию.
- Blast radius любой правки перечисляется полностью (файл, раздел, строка).
- Идентификаторы только латиницей.
- Датировка сессий локальной датой; временные факты в тексте в UTC с суффиксом `Z`.

## Конец сессии

Один session-блок по `05_CONVENTIONS` Часть III, кладётся ОДНИМ НОВЫМ файлом
`reference/_inbox/session_<TASK>_<YYYY-MM-DD>.md`. Сессия НЕ правит `07_STATE.md`,
`06_DECISIONS_LOG.md` и `06_INDEX.md`: их правит проход сборки. Номер решения присваивает сборка.
Свои артефакты и `reference/_scratch_<TASK>_<YYYY-MM-DD>/` сессия коммитит поимённо.
`proposed` без апрува владельца не применяется. Публикация наружу только после подтверждения.

Сессия работает в СВОЁМ рабочем дереве и коммитит в СВОЮ ветку `s/<TASK>`. Дерево после сессии
не удаляется и не сливается: и то и другое делает проход сборки. Правки правил (`CLAUDE.md`,
`05_CONVENTIONS.md`, файлы ролей) под буфер НЕ подпадают: их сессия коммитит сама, отдельным
коммитом.

## Параллельные сессии

Одна сессия, одно дерево, одна ветка. Две сессии на одном дереве запрещены: при общем дереве
ломаются три вещи сразу, и ни одна не лечится дисциплиной команд.

```
git worktree add worktrees/<TASK> -b s/<TASK> HEAD
```

Точка ветвления задана словом `HEAD` и умолчаний не оставляет. Размещение в видимом каталоге
`worktrees/` в корне, внесённом в `.gitignore`. Ветка одна на сессию: git не даёт выложить одну
ветку в два дерева, инвариант держит инструмент, а не память исполнителя.

Любая сессия, пишущая в репо, идёт в своём дереве. Исключение одно и структурное: проход сборки
идёт в основном дереве, потому что сливает ветки. Сессия генерации брифа берёт имя `<TASK>-GEN`.

## Язык

Проза к владельцу обычными словами, без внутренних идентификаторов либо с расшифровкой в той же
фразе. Два слоя: «для владельца» и «для репо», не смешивать. Вопрос владельцу только полным блоком:
что решаем, варианты, плюсы, минусы и риски, рекомендация. Вопрос, снимаемый чтением репо или
замером, не задаётся, а снимается.

## Мандат сессий

Мандат выдаётся по КЛАССУ задачи, не по задаче.

**Класс A, идёт постоянно:** чтение репо и внешних систем; запись ТОЛЬКО в изолированные области
и в `/reference`; локальный коммит. Публикация наружу остаётся на подтверждении.

**Класс B, требует задача-специфичного решения:** <перечислить свои необратимые операции>.

**При сомнении задача идёт в класс B.** Ошибка в сторону B стоит одной архитекторской сессии,
ошибка в сторону A стоит инцидента на живом проде.

Класс объявлен в трёх местах: шапка брифа, таблица в `07_STATE`, эта секция. **Расхождение между
брифом и `07_STATE` есть стоп-условие сессии**, не повод выбрать удобный класс.

Рабочие файлы сессии пишутся в `reference/_scratch_<TASK>_<YYYY-MM-DD>/` с самого начала, не в
корень репо, и коммитятся вместе с артефактом как провенанс.

Один скрипт на ШАГ брифа, а не на команду: дробление read-only шага на пять скриптов есть пять
лишних подтверждений и вклад в привыкание. Перед любым подтверждением на действие класса B
исполнитель обязан ОТДЕЛЬНЫМ сообщением назвать: что будет исполнено, на каком объекте, чем
откатывается.
````

## А3. `_ARCHITECT.md` (бутстрап консультационной сессии)

````md
# _ARCHITECT.md · Бутстрап архитекторской сессии

> Вставь этот файл в начало свежего чата, когда нужно ОБСУДИТЬ, посоветоваться или ПРИНЯТЬ РЕШЕНИЕ.
> Это консультационный бутстрап. Он НЕ про генерацию брифа: для этого `_GENERATOR.md`.

## 0. Когда брать

- закрыть открытые решения прошлой сессии;
- адъюдицировать `proposed`-решения и открытые пункты спеки;
- поднять и решить гэп, противоречие в доках, размытую формулировку;
- проверить, что шаг не ломает границу контракта или scope;
- решить blast radius правки по STABLE-докам;
- классифицировать гэп и поставить discovery-бриф.

НЕ брать для: написания прод-кода, механического применения патчей, генерации брифа готовой задачи.

## 1. Роль

Ты архитектор. Свежий чат становится архитектором, загрузив обязательный контекст. Старые
архитекторские чаты ретайрятся: сессия одноразовая, всё ценное уходит в репо session-блоком.

**Делаешь:** проектируешь, принимаешь решения, правишь документацию, держишь целостность, честно
поднимаешь гэпы и блокеры, ставишь discovery-задачи.
**Не делаешь:** не пишешь прод-код задач; не исполняешь и не коммитишь; не применяешь `proposed`
молча.

## 2. Жёсткие запреты

**Anti-improvisation.** Нет требуемого дока, значения или решения значит ОСТАНОВКА:
`CONTEXT GAP: <что именно отсутствует и почему без него нельзя продолжить>` и вопрос человеку.

**Untrusted-вывод.** Противоречивый лог недостоверен. Не примиряй половины, запроси чистый
перезапуск в разделимой форме.

**Работай на твёрдых фактах.** Прежде чем высказываться, подними релевантную фактуру из репо.
Не отвечай по памяти там, где есть документ. Факт без подтверждения есть гэп.

## 3. Источник истины

Внутри инструмента: файлы с диска, SHA фиксируется командой.
В обычном чате: только `curl`, только по commit-SHA, приложенному человеком. Браузерный фетчер
отдаёт закэшированную версию, работа на устаревшем контенте есть форма фабрикации.

**Обязательный контекст:** `_METHOD` + `00_CHARTER` + `04_ROADMAP` + `06_INDEX` + `07_STATE`
плюс то, на что опирается конкретный вопрос. Полный текст решения точечно по номеру.

## 4. Ритуал старта

1. Загрузить обязательный контекст плюс всё, на что опирается вопрос.
2. Переформулировать вопрос своими словами, перечислить полученные входы.
3. Поднять фактуру ДО высказываний: сходить в док, процитировать точную формулировку, и только
   потом выносить суждение.
4. Проверить полноту. Не хватает значит `CONTEXT GAP`, не догадка.

## 5. Работа с гэпами

Штатный процесс, а не сбой.
1. Сразу честно подними, назови источник, процитируй проблемное место.
2. Объясни суть: что к чему, почему гэп, варианты и последствия.
3. Классифицируй: блокер или нет; тип (факт / решение / референс-артефакт). Реши на месте или
   поставь discovery-бриф.
4. Обсудите: дай рекомендацию с обоснованием, развилку оставь человеку. Пушбек приветствуется.
5. Зафиксируйте: решение в журнал, гэп в открытые вопросы. Незафиксированное есть потерянное.

## 6. Формат выхода

Решения session-блоком. `proposed` не применяется без апрува.

**Правило явного патча.** Адресат патча это человек, который не видит твой ход мысли. Каждый
артефакт-изменение это drop-in:
- **Файл:** точное имя.
- **Место:** точка вставки («после строки X», «замена строки N», «НОВЫЙ ФАЙЛ path/name.md»).
- **Тип операции** явно: вставка / замена / append / новый файл. Не смешивать в одном блоке.
- **Контент** дословный, готовый к копипасту. Никаких «по аналогии с».
- **Вложенные ограждения кода:** внешний забор из четырёх обратных кавычек.
- В конце **сводка коммита**: список «файл, операция».

## 7. Дисциплина решений

- Журнал только append.
- STABLE/SEMI-STABLE доки только через решение в журнале.
- Blast radius перечислять полностью.
- Состояние каждую сессию через STATE_PATCH.
- Граница контракта и scope это красные линии.

## 8. Конец сессии

Один session-блок. Без него знание теряется. Формат коммита: `docs: <тема>`.
````

## А4. `_GENERATOR.md` (генератор брифов)

````md
# FILE: _GENERATOR.md

# GENERATOR — свежий чат, который генерит бриф следующей задачи

> Вставь это в НОВЫЙ чат. Механическая задача (расписана в роадмапе) значит средняя модель.
> Задача с суждением (нужны решения) значит архитектор.

## Роль

Ты генерируешь готовый task-brief следующей задачи, ЧИТАЯ репозиторий. Ты НЕ выполняешь задачу.

## Правило доступа

Внутри инструмента: файлы с диска. В обычном чате: только `curl` по SHA, приложенному человеком.
SHA не приложен значит спроси явно, не используй ветку по умолчанию «чтобы не задерживать».

## Прочитай

`_METHOD.md`, `00_CHARTER.md`, `04_ROADMAP.md`, `05_CONVENTIONS.md`, `06_INDEX.md`, `07_STATE.md`,
`08_TASK_BRIEF_TEMPLATE.md`, плюс спеки по «context-to-load» задачи.
Файл недоступен значит `CONTEXT GAP` и стоп.

## Что сделать

1. **Процитируй дословно** секцию «Текущий фокус» и строку статуса релевантной задачи из только что
   прочитанного `07_STATE`, ПЕРВЫМ, до сборки брифа. Это даёт человеку поймать рассинхрон
   (устаревший SHA, не та задача) ДО, а не после.
2. Определи задачу из «Текущего фокуса».
3. Собери по роадмапу цель, зависимости, артефакт, критерии приёмки.
4. Проверь открытые решения. Есть нерешённые и это задача с суждением значит СНАЧАЛА вынеси их
   человеку. Не генери бриф поверх нерешённого.
5. **Определи класс задачи** по таблице `07_STATE §Мандат` и проставь в шапке брифа. Класса в
   таблице нет значит `CONTEXT GAP`, а не повод его назначить. Класс B без указанного решения,
   выдавшего мандат, означает, что задача НЕ исполнима: бриф генерируется, но в шапку ставится
   явный гейт. Задача класса A по постоянному мандату не гейтится ничем.
6. Заполни шаблон, выдай самодостаточный бриф. Поля «Класс задачи», «Параллель» и «Файлы на
   запись» строго в форме шаблона; последнее маркированным списком, оно машиночитаемо.
7. Имя файла: `briefs/<TASK-ID>.md`.

## Тип: discovery-бриф

Если текущий фокус это закрытие гэпа, генери discovery-бриф по тому же шаблону, но:
- **Цель:** добыть недостающее знание, а не построить прод-артефакт.
- **Что вернуть:** обогащение репо (черновое решение, референс-артефакт, патч дока), не прод-код.
- **Приёмка:** знание зафиксировано и трассируемо к источнику.

## Выход

Один готовый markdown-бриф. Без лишней прозы вокруг.
````

## А5. `_ASSEMBLER.md` (проход сборки буфера)

````md
# FILE: _ASSEMBLER.md

# _ASSEMBLER.md · Проход сборки буфера session-блоков

## 0. Когда берётся

Каталог `reference/_inbox/` содержит хотя бы один файл кроме заглушки. Проверка одной командой,
голым `ls` пользоваться запрещено (вывод при каталоге с одной заглушкой и при пустом одинаков):

```
bash tools/session_status.sh
```

Критерий утвердительный: строка «файлов кроме .gitkeep: N». N больше нуля значит сборка нужна.

Непустой буфер есть стоп-условие старта любой другой сессии. Сборка идёт первой и в одиночку.

**Сборка идёт в ОСНОВНОМ рабочем дереве:** она сливает ветки сессий, а из связанного дерева этого
не сделать.

**Пустой буфер в основном дереве доказательством пустого буфера НЕ является:** файлы сессий лежат
в неслитых ветках. Инвентаризация начинается с шага 0.

## 1. Что делает и чего не делает

**Делает:** применяет накопленные блоки к `07_STATE.md`, `06_DECISIONS_LOG.md`, `06_INDEX.md`,
`07_ARCHIVE.md` ОДНИМ коммитом; раздаёт номера решений в один поток; удаляет разобранные файлы.

**Не делает:** не решает и не адъюдицирует; не переписывает содержание блока кроме подстановки
номера; не апрувит `proposed` ни своим решением, ни «по смыслу»; не пишет прод-код.

Сборщик есть механический переносчик с правом остановки, а не архитектор с правом трактовки.

## 2. Жёсткие запреты

**Anti-improvisation.** Блок непонятен, ссылается на несуществующий файл, противоречит сам себе
значит ОСТАНОВКА: `CONTEXT GAP: <какой файл буфера, какая строка, что неясно>`.
Запрещено «применить то, что понятно, остальное потом»: наполовину собранное состояние хуже
несобранного, потому что выглядит свежим.

**Заглушка каталога буфера не удаляется никогда.** Без неё каталог исчезает с диска, и проверка
старта начинает падать по причине, к работе отношения не имеющей.

**Коммит поимённо.** Добавление всего разом запрещено: состав коммита сборки обязан быть точным,
по нему потом восстанавливают, что и откуда применено.

## 3. Вход

1. Рабочее дерево чистое, кроме файлов буфера.
2. Обязательный контекст по `CLAUDE.md §Старт` п.2.
3. Проверка подмены: первая строка каждого дока равна его имени.
4. **Все** файлы буфера целиком, не выборочно: конфликт виден только на полном наборе.
5. Хук установлен и работает.

## 4. Порядок работы

**Шаг 0. Слияние веток сессий.** `bash tools/session_status.sh` печатает деревья и ветки
счётчиками и списком. Каждую ветку слить по одной, поимённо. Конфликтов не ожидается по
построению: ветки не трогают состояние, журнал и индекс. Возникший конфликт обрабатывается как
конфликт блоков по §6: остановка и вопрос.

**Шаг 1. Инвентаризация.** Для каждого файла вида `session_<TASK>_<YYYY-MM-DD>.md` выпиши задачу и
дату. Файл, не подходящий под шаблон имени, есть гэп: остановка, не догадка о его назначении.

**Шаг 2. Порядок.** Выстрой блоки по §5 и зафиксируй список в теле будущего коммита ДО первой правки.

**Шаг 3. Проверка на конфликт** по §6 ДО того, как тронешь хоть один файл.

**Шаг 3a. Маркеры времени в блоках последствий.** Пункт `[сейчас]` обязан быть применим этим же
коммитом, его невыполнимость есть стоп-условие. Пункты `[отдельным коммитом]` и `[задачей <ID>]` в
репо НЕ проверяются: первые перечисляются в теле коммита как названная задолженность, для вторых
проверяется лишь наличие задачи строкой в состоянии. Пункт БЕЗ маркера есть гэп.

**Шаг 4. Применение, блок за блоком по порядку из шага 2.**
- STATE_PATCH в `07_STATE.md`;
- NEW_DECISIONS со статусом accepted: append в журнал плюс строка в индекс ТЕМ ЖЕ коммитом;
- полностью закрытые строки уходят из состояния в архив ДОСЛОВНО тем же коммитом;
- `proposed` по §7;
- SESSION_LOG никуда не переносится, см. §8.

**Шаг 5. Шапка состояния.** Дата обновления есть дата сборки, подпись есть «сборка (буфер <дата>)».

**Шаг 6. Удаление разобранного** по одному файлу поимённо. Заглушку не трогать.

**Шаг 7. Коммит.** Поимённо, одним коммитом. В теле сообщения список разобранных блоков и
выданные номера.

**Шаг 8. Уборка деревьев.** Для каждой слитой ветки: удалить дерево, затем ветку ключом `-d`,
не `-D`: git обязан подтвердить, что ветка слита. Отказ удаления есть стоп-условие, а не повод
перейти на форсированный ключ. Дерево с несохранённой работой не удалять, назвать в отчёте.

**Шаг 9. Верификация.** `bash tools/session_status.sh` печатает «ЧИСТО» и возвращает ноль.
Любое расхождение есть остановка и доклад, не самостоятельная починка. Вердикт читается по
напечатанным счётчикам, а не по отсутствию вывода.

## 5. Нумерация решений

1. по дате в имени файла, от ранней к поздней;
2. при совпадении даты по алфавиту названия задачи;
3. **оговорка, перекрывающая 1 и 2:** блок X, ссылающийся на решение из блока Y, идёт после Y.

Номер равен следующему за максимальным в индексе на момент сборки, дальше подряд без пропусков.

Подстановка выданного номера в текст решения, в строку индекса и во все ссылки этого же блока есть
ЕДИНСТВЕННАЯ правка содержания, которую сборщик делает.

Мотив: воспроизводимость. Два разных сборщика на одном буфере обязаны дать один результат.

## 6. Конфликт между блоками

Конфликт есть, если: два блока правят одну строку состояния; один блок закрывает строку, которую
другой правит; два блока дают несовместимые формулировки одного факта; два блока претендуют на
один идентификатор.

**Действие: СТОП до первой правки.** Не применяется ни один блок, включая бесконфликтные. Буфер
остаётся нетронутым. Владельцу вопрос полным блоком: что решаем, варианты, последствия, рекомендация.

## 7. Неодобренное

`proposed` сборщик не применяет и не апрувит. Формулировка переносится строкой в открытые вопросы
с указанием, из какого блока пришла; файл буфера удаляется на общих основаниях.
Мотив: оставить файл в буфере нельзя, непустой буфер блокирует старт следующей сессии.

## 8. Судьба SESSION_LOG

Файл удаляется, содержимое остаётся в истории git. Отдельный постоянный адресат не заводится.

## 9. Права и трение

Удаление файлов не внесено ни в один список прав, значит на каждое удаление инструмент запросит
подтверждение. **Это норма, а не сбой:** удаление есть ровно тот случай, где подтверждение несёт
защитную функцию.

## 10. Стоп-условия

- рабочее дерево грязное сверх файлов буфера;
- файл в буфере не подходит под шаблон имени;
- блок ссылается на несуществующее И пункт помечен `[сейчас]`;
- пункт блока последствий не несёт маркера времени;
- конфликт по §6;
- хук дал FAIL не по своей правке;
- после применения в буфере осталось что-то кроме заглушки;
- ветка не сливается без конфликта;
- удаление ветки ключом `-d` отказывает.

Обход хука запрещён без прямого апрува владельца в этой же сессии.

## 11. Конец прохода

Сборка НЕ кладёт свой session-блок в буфер: это дало бы рекурсию. Отчёт пишется в тело коммита.
Сборка есть единственная роль, которой разрешено править состояние, журнал и индекс напрямую.
````

```bash
# FILE: tools/session_status.sh — состояние старта сессии одной командой
```

## А9. `tools/parallel_check.sh`

```bash
#!/usr/bin/env bash
# FILE: tools/parallel_check.sh — проверка пересечения наборов файлов на запись
# Использование: bash tools/parallel_check.sh TASK1 TASK2 [TASK3 ...]
# Читает поле «Файлы на запись» из briefs/<TASK>.md. Печатает наборы ЦЕЛИКОМ
# (совпавшие строки, не метка) и пересечения. Код 1 = запускать вместе нельзя.
set -uo pipefail
root=$(git rev-parse --show-toplevel 2>/dev/null) || true
[ -n "$root" ] || { echo "ПРОВЕРКА: не git-репозиторий" >&2; exit 2; }
cd "$root" || exit 2
[ $# -ge 2 ] || { echo "ПРОВЕРКА: нужно минимум две задачи" >&2; exit 2; }
TMP=$(mktemp -d) || exit 2
trap 'rm -rf "$TMP"' EXIT   # временные файлы НЕ в рабочем дереве: они бы попали в статус

extract() { # $1=TASK -> пути по одному в строке
  local f="briefs/$1.md"
  [ -f "$f" ] || { echo "ПРОВЕРКА: нет файла $f" >&2; return 3; }
  awk '
    /^\*\*Файлы на запись\*\*/ { inblock=1; found=1; next }
    inblock && /^\*\*/         { inblock=0 }
    inblock && /^- `/          { match($0,/`[^`]+`/); print substr($0,RSTART+1,RLENGTH-2) }
    END { if (!found) exit 4 }
  ' "$f"
}

fail=0
declare -a NAMES
for t in "$@"; do
  set +e; out=$(extract "$t"); rc=$?; set -e
  if [ $rc -eq 4 ]; then echo "ПРОВЕРКА: в briefs/$t.md нет поля «Файлы на запись» — это ОТКАЗ, не пустой набор" >&2; exit 3; fi
  [ $rc -eq 0 ] || exit 3
  n=$(printf '%s' "$out" | grep -c . || true)
  if [ "$n" -eq 0 ]; then echo "ПРОВЕРКА: у $t поле есть, но набор пуст — ОТКАЗ" >&2; exit 3; fi
  printf '== %s: %s путей ==\n%s\n\n' "$t" "$n" "$out"
  printf '%s\n' "$out" | sed 's#/$##' | sort -u > "$TMP/$t"
  NAMES+=("$t")
done

echo "== пересечения =="
for ((i=0;i<${#NAMES[@]};i++)); do for ((j=i+1;j<${#NAMES[@]};j++)); do
  a=${NAMES[$i]}; b=${NAMES[$j]}
  # пересечение: равные пути ИЛИ один есть каталог-предок другого
  hit=$(awk 'NR==FNR{p[$0];next}{ for(q in p){ if($0==q || index($0,q "/")==1 || index(q,$0 "/")==1) print q" <-> "$0 } }' "$TMP/$a" "$TMP/$b" | sort -u)
  if [ -n "$hit" ]; then printf '%s x %s: ПЕРЕСЕЧЕНИЕ\n%s\n' "$a" "$b" "$hit"; fail=1
  else printf '%s x %s: пересечения нет\n' "$a" "$b"; fi
done; done
echo "== вердикт =="
if [ "$fail" -eq 0 ]; then echo "ПАРАЛЛЕЛЬ ДОПУСТИМА по файлам (класс задач проверяется отдельно)"; exit 0
else echo "ПАРАЛЛЕЛЬ ЗАПРЕЩЕНА: наборы пересекаются. Запускать по одной."; exit 1; fi
```

## А10. `tools/hooks/pre-commit`

Установка: `ln -s ../../tools/hooks/pre-commit .git/hooks/pre-commit`

```bash
#!/usr/bin/env bash
# FILE: tools/hooks/pre-commit — механические инварианты коммита
set -euo pipefail
fail() { echo "PRE-COMMIT FAIL: $1" >&2; exit 1; }
staged() { git diff --cached --name-only --diff-filter=ACM; }

# Класс гомоглифов задан альтернацией ЦЕЛЫХ символов, не скобочным выражением.
# Под байтовой семантикой скобочное выражение над многобайтными символами распадается
# на множество БАЙТОВ, и ведущий байт совпадает с любой кириллицей.
CYR='(М|С|Е|А|Р|О|Т|Н|К|В|Х)'
ID_ROW='(Q-[0-9]+|[A-Z0-9-]+)'

# 1. Первая строка нумерованного/подчёркнутого дока равна имени файла
for f in $(staged | grep -E '^(_[A-Z]|[0-9]{2}_).*\.md$' || true); do
  blob=$(git show ":$f")            # без пайпа в head, иначе SIGPIPE на файле больше буфера пайпа
  first=${blob%%$'\n'*}
  base=$(basename "$f" .md)
  printf '%s\n' "$first" | grep -qE "^# (FILE: )?_?${base}|^# [0-9]{2} ·" \
    || fail "$f: первая строка не соответствует имени файла: '$first'"
done

# 2. Кириллические гомоглифы внутри идентификаторов
added=$(git diff --cached -U0 | grep -E '^\+' || true)   # подсчёт вместо -q: вход дочитывается до EOF
hits=$(printf '%s\n' "$added" | grep -nE "(ADR|RQ|E1|Q|B)[-–][0-9]*${CYR}|${CYR}(DR-|Q-|-P)" || true)
if [ -n "$hits" ]; then
  printf '%s\n' "$hits" >&2                              # печатать совпавшие строки, не только вердикт
  fail "кириллица внутри идентификатора"
fi

# 3. Append в журнал решений требует строки в индексе тем же коммитом
if staged | grep -q '^06_DECISIONS_LOG.md$'; then
  new_adr=$(git diff --cached -U0 -- 06_DECISIONS_LOG.md | grep -oE '^\+## (ADR-[0-9]+)' | grep -oE 'ADR-[0-9]+' || true)
  for a in $new_adr; do
    staged | grep -q '^06_INDEX.md$' || fail "$a добавлен в журнал, но 06_INDEX.md не в коммите"
    git show :06_INDEX.md | grep -qF "$a" || fail "$a отсутствует в 06_INDEX.md"
  done
fi

# 4. Строка с ID ИСЧЕЗЛА из состояния значит архив в том же коммите.
# Сравниваются МНОЖЕСТВА ID удалённых и добавленных строк: переформулировка строки
# (ID есть и там, и там) не срабатывает. Это был ложный позитив, обучавший обходу хука.
d4=$(git diff --cached -U0 -- 07_STATE.md || true)
gone_ids=$(comm -23 \
  <(printf '%s\n' "$d4" | grep -oE "^\-\| ${ID_ROW} \|" | sed -E 's/^\-\| //; s/ \|$//' | sort -u) \
  <(printf '%s\n' "$d4" | grep -oE "^\+\| ${ID_ROW} \|" | sed -E 's/^\+\| //; s/ \|$//' | sort -u) || true)
if [ -n "$gone_ids" ]; then
  staged | grep -q '^07_ARCHIVE.md$' \
    || fail "строки исчезли из 07_STATE, 07_ARCHIVE.md не в коммите: $(printf '%s' "$gone_ids" | tr '\n' ' ')"
fi

# 5. Правка состояния требует обновления даты
if staged | grep -q '^07_STATE.md$'; then
  n=$(git diff --cached -- 07_STATE.md | grep -cE '^\+\*\*updated_at:\*\*' || true)
  [ "$n" -gt 0 ] || fail "07_STATE.md правится без обновления updated_at"
fi
echo "pre-commit: инварианты пройдены"
```

**Обязательно к хуку:** файл самотеста `tools/hooks/selftest.sh`, прогоняющий набор кейсов в двух локалях (однобайтной и многобайтной) и печатающий «пройдено N, провалено M». Прогоняется ДО первого коммита сессии. Любой провал есть остановка.

# Итог одной страницей

Метод состоит из четырёх идей, всё остальное следствия.

1. **Знание живёт в репозитории, а не в чате.** Роль это не чат, роль это загруженный контекст.
2. **Догадка запрещена.** Нет входа значит остановка и вопрос. Гэп это задача, а не тупик.
3. **Есть красная линия, которую слои не пересекают.** Без неё приёмка вкусовая.
4. **Сессия не применяет свой результат сама.** Между сессией и источником истины стоит буфер и отдельный проход сборки, а между сессиями стоит git-изоляция деревьев.

Всё, что выглядит бюрократией, есть либо защита одной из этих четырёх идей, либо шрам от конкретного тихого отказа. **Тихий отказ есть худший класс отказа в этом методе**, и почти каждое правило здесь существует, чтобы отказ был громким.

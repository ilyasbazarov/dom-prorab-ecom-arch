## BITRIX-B2-08 (P-08) — Три несогласованных списка стадий сделки в разных частях ТЗ

**Проблема.** Единого канонического перечня стадий воронки в корпусе нет. Три фрагмента
называют разные наборы:
- `CRM-LM-01` — 10 стадий воронки чекаута.
- Последняя миля — вводит стадии вне этого списка и переименовывает терминальную.
- Реестр WA HSM-шаблонов — 9 логических `stage_id`, не совпадающих по числу и именам ни с
  одним из двух списков выше.

**Контекст.**
- `CRM-LM-01`: `d4_t02_cross_sell_bundle_korzina_i_chekaut.md@eb134244b706f4d123fa5f9b6b7441236cdc230d:668-679`
  — «Новая», «Ожидает подтверждения», «Ожидает оплаты», «Оплачено», «В работе/Ожидает
  сборки», «Требует уточнения», «Сборка завершена», «Ожидает выдачи», «Выполнен/Получен»,
  «Отменена» (10 строк).
- Последняя миля: `d4_t04_poslednyaya_milya_vozvraty_reklamatsii.md@eb134244b706f4d123fa5f9b6b7441236cdc230d:88`
  (стадия «Сборка завершена» присваивается CRM-роботом для delivery-ветки), `:173`
  («Передан курьеру» — стадия отсутствует в CRM-LM-01 как отдельное имя), `:203,271,359,379-380`
  (терминальная стадия названа «Успешно реализовано», а не «Выполнен/Получен» из CRM-LM-01),
  `:331` («Сделка → «Ожидает вебхука order_completed» (промежуточный статус)» — стадия,
  которой нет ни в одном из двух других списков).
- Реестр WA-шаблонов: `d4_t07_reestr_wa_hsm_shablonov.md@eb134244b706f4d123fa5f9b6b7441236cdc230d:51,609`
  — «Логические stage_id (OQ-01 закрыт): NEW, PRE_CONFIRM, PAID, PICKING, OOS_QUERY, PICKED,
  READY, DONE, CANCEL» (9 значений).
- Канон: `l0-canon/canonical_order_flow.md` §3 — 10 канонических строк CRM-стадия→ЛК с
  провенансом; canonical список не тождественен буквально ни одному из трёх фрагментов выше.

**Изменение.** Только текст, без изменения бизнес-логики:
- Свести все перечисления стадий сделки (CRM-LM-01, последняя миля, реестр WA-шаблонов,
  Эпик 21 если правится по BITRIX-B2-18) к одному именованию, совпадающему с
  `l0-canon/canonical_order_flow.md` §3 (10 строк, левая колонка).
- Явно сопоставить 9 логических `stage_id` реестра WA-шаблонов с 10 каноническими стадиями
  (какие два канонических имени делят один `stage_id`, если это осознанное решение —
  описать явно, не оставлять implicit).
- Заменить «Успешно реализовано» либо «Выполнен / Получен» — оставить одно имя терминальной
  стадии повсеместно.
- Добавить стадию «Передан курьеру» и промежуточную «Ожидает вебхука order_completed»
  (если сохраняется) в единый канонический перечень или обосновать, почему они не являются
  самостоятельными стадиями воронки (`STATUS_ID`).

**Критерии приёмки.**
- Один документ/раздел содержит полный список стадий воронки; остальные фрагменты ссылаются
  на него, а не дублируют с расхождениями.
- Список 1:1 соответствует `l0-canon/canonical_order_flow.md` §3 по числу и именам строк
  (10), либо канон правится отдельным ADR при обоснованном расхождении (не в этом тикете).
- `stage_id` реестра WA-шаблонов покрывает все 10 канонических стадий явным маппингом
  (может быть N:1, но задокументированным, не implicit).

**Трассировка:** F5-01 · P-08 · CQ-05 (факт. `crm.dealcategory.stage.list` с портала —
закрывает вопрос, какие `STATUS_ID` реальны, этот тикет решает только согласованность текста).

## BITRIX-B2-12 (P-12) — `OOS_QUERY` держит два разных триггера под одним логическим `stage_id`

**Проблема.** Слой наблюдаемости (v1.1, правка CONTRA-2) разделил старую единую стадию
«Частичный OOS» на две разные: «Требует уточнения (Нехватка)» (нехватка при создании
заказа) и «Уточнение состава» (нехватка при сборке). Реестр WA HSM-шаблонов при этом
продолжает держать оба триггера под одним логическим `stage_id` `OOS_QUERY`.

**Контекст.**
- Разделение: `d4_t05_sloy_nablyudaemosti_za_infrastrukturoy.md@eb134244b706f4d123fa5f9b6b7441236cdc230d:420`
  (changelog v1.1, CONTRA-2: «MON-06 „Частичный OOS“ → два корректных статуса „Требует
  уточнения (Нехватка)“ + „Уточнение состава“»), подтверждено `:270-272` (два разных
  триггера: `/create_order`=`partial` — Эпик 17.1; вебхук `oos_at_picking` от 1С — Эпик 19.1).
- Схлопывание: `d4_t07_reestr_wa_hsm_shablonov.md@eb134244b706f4d123fa5f9b6b7441236cdc230d:58`
  («OOS_QUERY | /create_order = partial → переход»), `:60` («PICKING | Вебхук oos_at_picking
  → OOS_QUERY») — оба триггера ведут в один `stage_id`.
- Канон: `l0-canon/canonical_order_flow.md` §3 держит их двумя отдельными строками
  («Требует уточнения (Нехватка) — partial» / «Уточнение состава — oos_at_picking
  (мутация)»), обе с отображением в ЛК «Комплектуется», но с разным провенансом.

**Изменение.** Только текст, без изменения бизнес-логики:
- Развести `OOS_QUERY` на два логических `stage_id` (например `OOS_CREATE` / `OOS_PICKING`,
  предложение уже есть в источнике проблемы `problem_register.source.md:253`, решение —
  за подрядчиком) — согласовать с канонической парой строк §3.
- Если два триггера НАМЕРЕННО делят один `stage_id` (напр. потому что WA-шаблон и таймер
  эскалации у них общие) — явно это записать вместо implicit совпадения кода.

**Критерии приёмки.**
- В реестре WA-шаблонов однозначно видно, какой `stage_id` соответствует «Требует
  уточнения (Нехватка)», а какой — «Уточнение состава» (либо явное обоснование общего кода).
- Соответствие каждой из двух строк канона §3 (Требует уточнения / Уточнение состава)
  проверяемо по тексту тикета.

**Трассировка:** F5-01 · P-12.

# CLAUDE.md — законы Claude Code-сессий проекта dom-prorab-ecom-arch (ADR-029, пилот)

Ты работаешь в локальном клоне репо `ilyasbazarov/dom-prorab-ecom-arch` — источника истины
проекта интеграции 1С:УТ ↔ Bitrix24 CRM ↔ Bitrix CMS (Dom Prorab, Бишкек). 1С — мастер
операционной истины; CMS→1С напрямую запрещено, только через CRM. Правила — docs/01_CONVENTIONS.md;
роли — docs/03_ROLES.md; протокол сессий — docs/04_SESSION_PROTOCOL.md.

## Старт каждой сессии (обязательный порядок)

1. `git status` — рабочее дерево чистое; `git rev-parse HEAD` — это SHA сессии: зафиксируй его
   в session-блоке и используй в цитатах (файл@SHA:строки). Дерево грязное → стоп, вопрос владельцу.
   НЕ работай поверх чужих незакоммиченных правок.
2. Прочитай обязательный контекст: docs/01_CONVENTIONS.md + docs/00_STATE.md +
   docs/02_ADR_INDEX.md + docs/05_ROADMAP.md + docs/03_ROLES.md + l0-canon/project_goal.md. Полный текст конкретного ADR —
   точечно из docs/02_ADR_LOG.md по номеру; закрытые строки STATE — точечно из
   docs/00_STATE_ARCHIVE.md (К-19).
3. Проверка К-20: первая строка каждого прочитанного docs/NN_*.md и этого файла = `# FILE: <путь>`.
   Не совпало → `СОДЕРЖИМОЕ НЕ ТО: <файл> — ожидалось <что>, внутри <что>` и стоп.
4. Хук установлен и РАБОТАЕТ:
   `test -x .git/hooks/pre-commit || ln -s ../../tools/hooks/pre-commit .git/hooks/pre-commit`
   затем `bash tools/hooks/selftest.sh` — ожидание «провалено 0». Любой провал → стоп, вопрос
   владельцу: сломанная проверка хуже отсутствующей (отказ тихий). До первого коммита, не после.
5. Переформулируй задачу своими словами, перечисли входы, проверь полноту.

## ★ Законы (нарушение любого = провал сессии)

- **Человеческий язык (К-16, К-39).** Правило номер один. Проза к владельцу — обычными словами; вопрос
  владельцу — только полным блоком: что решаем → варианты → векторы/последствия → рекомендация
  отдельной строкой. Выход делится надвое: текст к владельцу и машинная часть (session-блок,
  FILE_PATCHES, брифы, содержимое файлов репо); в машинной части коды свободны. Форма текста к
  владельцу задана К-39: шапка из трёх строк «Сделано / Нужно от Owner / Рекомендация», дальше не
  более 25 строк, тезис плюс одна поясняющая фраза. Коды проекта употребляются как есть, расшифровка
  не требуется. Блока самопроверки и любых иных хвостовых блоков после машинной части нет (ADR-074).
- **Anti-improvisation.** Нет дока/значения/решения → `CONTEXT GAP: <что и почему блокирует>`,
  стоп, вопрос владельцу. Выдумывать, «дотягивать», подставлять правдоподобное запрещено.
- **Фактура до суждения (К-1).** Подними файл, процитируй файл@SHA:строки, потом мнение.
  SHA = `git rev-parse HEAD` этой сессии.
- **Красные линии.** l3-external/ immutable (К-3). Конфликт L0↔L3 = дефект документации
  подрядчика (К-2). Решения проекта не принимаешь: развилки — владельцу; `proposed` без апрува
  не применяется (К-15). В каком статусе запись выходит, задаёт К-40.
- **Append-only.** docs/02_ADR_LOG.md не редактируется, кроме строк статуса (ADR-016).

## Параллельные сессии (ADR-037 §5)

Две сессии на одном рабочем дереве запрещены. Правило действует до появления машинерии
параллельного контура (буфер, сборщик, отдельные деревья, машинные проверки — волна M2):
одновременная работа двух сессий в одном клоне даёт дрейф SHA под drop-in-правками, затирание
строк docs/00_STATE.md при двух блоках на одну строку и разъезд перекрёстных ссылок на номера
решений. Условие параллелимости и порядок её внедрения — ADR-037 §1 и §2.

## Мандат (ADR-049 §1, дополнен ADR-059 §1)

Внутрь Claude Code допускается закрытый перечень из шести ролей; роль вне перечня — только
новым ADR:
1. **Applier** — «Примени session-блок»: правила docs/04_SESSION_PROTOCOL.md §Правила
   применения, никакого творчества; после правок — коммит и блок «НА АРХ-РЕВЬЮ» владельцу.
2. **Executor** — «Исполни бриф <ID>» по prompts/executor.md.
3. **Architect режим A** — решения, ревью открытых вопросов и proposed-ADR, роудмап.
4. **Architect режим B** — выпуск брифов `briefs/<ID>.md` по docs/06_BRIEF_TEMPLATE.md.
5. **Reviewer** — ревью целостности по prompts/reviewer.md.
6. **Business** — бизнес-решения по prompts/business.md.

Ограничение ADR-029 §2 «ровно два режима» и ограничение «ОДИН бриф, названный владельцем»
сняты ADR-049 §1: это были свойства пилота, а не ролей.

Режим объявляется, а не перечисляется (ADR-049 §3): пусковое сообщение несёт отдельную строку
с именем режима этой сессии и перечня не воспроизводит. Перечень выше — единственный экземпляр.
Роль сверяет строку режима с ним отдельным шагом, до чтения обязательного контекста; режима в
перечне нет → стоп и вопрос владельцу (ADR-049 §4). Разовые исключения мандата строкой пускового
сообщения прекращены (ADR-049 §5).

**Класс B — необратимые операции (ADR-036 §1; подтверждён ADR-049 §2 и ADR-059 §2).** Перечень:
отправка пакета подрядчику · `git push` · правка `l3-external/raw`. Мандат сессии их не покрывает
никогда: каждая требует отдельного решения владельца и отдельного подтверждения перед
исполнением, независимо от пути и роли. При сомнении в классе — класс B. Всё остальное — класс A.

## Конец сессии

Один session-блок по docs/04_SESSION_PROTOCOL.md — текст вставь в описание коммита.
Формат коммита: `docs: <суть> (session <id>)`. Хук обязан пройти; `git commit --no-verify`
запрещён без явного апрува владельца (фиксируется в session-блоке). `git push` не выполняется
без явной команды владельца: по умолчанию коммиты копятся локально, пуш владелец делает сам.

- ADR-053 [ARCH]: Идемпотентный повтор /create_order — канон приводится к 1С; статус
  `duplicate` упраздняется
  Статус: accepted (Architect; вариант подтверждён Owner 2026-08-02)

  Контекст. Корпус описывает повтор /create_order тремя несовместимыми способами. 1С
  возвращает `{"status":"success","idempotent":true}` — блок «Идемпотентность»
  `d5_t01@8a7eedbb:1256-1274` и таблица «Ошибки и исключения» `d5_t01@8a7eedbb:1356`
  («Повторный CRM_Deal_ID | 200 | success + idempotent: true»); слово `duplicate` в d5_t01 не
  встречается ни разу. Интеграционный контракт и CRM-сторона ждут отдельный статус:
  `d1_t03@8a7eedbb:102`, `d4_t03@8a7eedbb:147`, приёмка AC-16.3 `d4_t03@8a7eedbb:165`. Внутри
  D5 расхождение продублировано: регистр логирования допускает `Response_Status = duplicate`
  и DoD требует «200 duplicate» (`d5_t02@8a7eedbb:120,162`). Канон закрепил прочтение D1
  (`l0-canon/canonical_order_flow.md@8a7eedbb:64`, источник — `:60`). Операционное следствие:
  матрица ответов D4 ключуется по `status` и строки «success + idempotent: true» для
  /create_order не содержит (`d4_t03@8a7eedbb:142-149`), поэтому фактический ответ 1С попадёт
  в ветку `success` (`:144`) — повторное WA клиенту и перевод сделки в «В работе / Ожидает
  сборки» с более поздней стадии. Для /update_order такая строка в той же матрице есть
  (`d4_t03@8a7eedbb:406`, «Лог. Без изменений состава»), то есть согласованный образец в
  корпусе уже существует. Ссылка `[DEC-15]` в строке D1 отношения к формату не имеет: DEC-15
  (`d5_t01@8a7eedbb:1751`) говорит о моменте вызова /create_order, не об ответе.

  Решение.
  1. Канонический формат идемпотентного повтора /create_order — `{"status":"success",
     "idempotent": true}` с заполненными `purchase_order_guid` и `purchase_order_number`.
     Сторона 1С не меняется.
  2. Статус `duplicate` объявляется несуществующим. Канон §4 T1 и §6 правятся.
  3. CRM обязана различать первичный и повторный success по флагу `idempotent`, а не по
     коду и не по статусу. При `idempotent: true`: сохранить `purchase_order_guid` если пуст,
     записать лог, НЕ отправлять WA, НЕ менять стадию сделки. Задача Bitrix-подрядчику,
     Track A, по образцу уже описанной строки `d4_t03@8a7eedbb:406`.
  4. Расхождение внутри D5 (`d5_t02@8a7eedbb:120,162`) — дефект документации подрядчика
     (К-2): значение `duplicate` из перечня `Response_Status` и из DoD убирается,
     идемпотентный повтор логируется как `success` с `Is_Duplicate = Истина`. Задача 1С,
     нулевая по коду.
  5. Выбор в пользу 1С, а не D1/D4, обоснован тем, что 1С формирует ответ, паттерн
     `success + idempotent` применяется в корпусе также к /update_order (`d5_t03@8a7eedbb:208,
     286,340`) и к /close_order (`d6_t05@8a7eedbb:97`), и приведение к нему делает контракт
     однородным по всем эндпоинтам.
  6. Принятый риск: наивный потребитель, читающий только `status`, при этом формате ломается
     тихо (повторит действия), тогда как отдельный статус ломал бы его громко. Компенсация —
     п.3 как явное требование приёмки задачи Bitrix, не как рекомендация.

  Последствия (blast radius). `l0-canon/canonical_order_flow.md` §4 T1 строка `:64` и §6
  строка `:102` (FILE_PATCHES ниже); `l2-registers/problem_register.md` — новая запись P-30;
  задача Bitrix-подрядчику волны Track A (ветка `idempotent`), задача 1С документационная по

  же, меняется только форма ответа.

- ADR-054 [ARCH]: Коды ответов эндпоинтов 1С выбираются по достижимости целевого состояния;
  правила «повтор=200 / невозможное действие=409» не существует
  Статус: accepted (Architect; вариант подтверждён Owner 2026-08-02)

  Контекст. Формулировка «Правило для всех эндпоинтов: повтор = 200, невозможное действие =
  409» происходит из `l2-registers/problem_register.source.md:362` и является предложением
  аналитика, а не цитатой ТЗ; бриф прямо требовал не объявлять её действующей
  (`briefs/F5-02.md@8a7eedbb:55-57`). Проверка корпуса правило не подтверждает.
  /cancel_reserve на уже отменённый заказ отвечает `HTTP 200 {"status":"already_cancelled"}`
  (`d5_t02@8a7eedbb:221`, продублировано `:288`); на уже закрытый («Выполнен»,
  «Реализован») — `HTTP 200 {"status":"already_closed","reason":"order_completed"}`
  (`d5_t02@8a7eedbb:222`, продублировано `:289`). /update_order на закрытый или отменённый
  заказ отвечает `HTTP 409, order_not_mutable` (`d5_t03@8a7eedbb:204,320,344,357`;
  CRM-сторона `d4_t03@8a7eedbb:408`). Оба паттерна документированы многократно и в разных
  файлах, опечаткой не являются.

  Решение.
  1. Единого правила по признаку «повтор / невозможное действие» нет и не вводится.
  2. Вводится критерий выбора кода: достигнуто ли целевое состояние вызова. Достигнуто (в том
     числе достигнуто ранее и иным путём) — HTTP 200 с уточняющим `status`. Недостижимо —
     HTTP 4xx с `reason`. Оба наблюдаемых паттерна объясняются этим критерием:
     у /cancel_reserve на закрытом заказе резерв уже снят проведением закрывающего документа,
     цель достигнута; у /update_order новый состав недостижим, потому что документ не
     мутабелен.
  3. Поведение /cancel_reserve и /update_order НЕ унифицируется. Изменений у подрядчиков
     ноль.
  4. Критерий обязателен к применению при спецификации новых эндпоинтов; отклонение
     оформляется ADR.
  5. P-17 закрывается как REFUTED в части «правило существует».

  Последствия (blast radius). `l0-canon/canonical_order_flow.md` §5 — добавляется строка
  критерия (FILE_PATCHES ниже); `l2-registers/problem_register.md` — новая запись P-17;
  `docs/02_ADR_INDEX.md` — новая строка. Задач подрядчикам не порождает.

- ADR-055 [ARCH]: Исходящий контур 1С→CRM — в корпусе ЧЕТЫРЕ URL-константы; четвёртая
  упраздняется, order_completed остаётся событием статус-канала. Корректирует ADR-017 §1
  Статус: accepted (Architect; п.2 меняет согласованное ТЗ 1С, подтверждён Owner 2026-08-02)

  Контекст. ADR-017 §1 зафиксировал «ТРИ канала, каждый со своим URL» на основании
  `d5_t06@723fe0a:217,223,256`. Строка `d5_t06@8a7eedbb:219` в это чтение не попала: реестр
  констант 4.3 содержит четыре URL-сущности — `CRM_Webhook_Path_CheckPrinted` (`:217`),
  `CRM_Webhook_URL_OrderStatus` (`:218`), `CRM_Webhook_URL_OrderCompleted` (`:219`),
  `CRM_Webhook_URL_OOS` (`:220`). Четвёртая используется задачей 1С-LM-02: подписка
  `ЛМ_РеализацияПослеПроведения` на ПослеПроведения документа «Реализация товаров», только
  для e-com + самовывоз + юрлицо, шлёт `event: "order_completed"` на константу
  `CRM_Webhook_URL_OrderCompleted` (`d5_t06@8a7eedbb:257`; спецификация
  `d5_t04@8a7eedbb:335,341,347`, payload `:405-415`, URL `:419`; сценарий
  `d6_t05@8a7eedbb:89,96`). Тот же `event` независимо отправляет подписка
  `СТ_ВебхукСтатус` на ПриЗаписи документа «Заказ покупателя» (`d5_t06@8a7eedbb:254`;
  `d5_t01@8a7eedbb:1445,1453`, URL `:1478`). Bitrix-подрядчику четвёртый эндпоинт не заказан:
  перечень пре-реквизитов называет два URL и прямо приписывает `order_completed` каналу
  OrderStatus (`d4_t03@8a7eedbb:602`, то же `:64`). При реализации по букве корпуса вебхук
  для юрлица на самовывозе уйдёт на несуществующий адрес, сделка останется в «Ожидает
  вебхука order_completed». Надёжность двух источников разная: 1С-РТ-03 при ошибке отправки
  пишет только WARN (`d5_t01@8a7eedbb:1482`), 1С-LM-02 имеет Retry×3 и DLQ с кнопкой
  переотправки (`d5_t04@8a7eedbb:422-430`). Ни один payload не несёт `doc_version`
  (`d5_t01@8a7eedbb:1460-1472`; `d5_t04@8a7eedbb:405-415`).

  Решение.
  1. Констатация факта: URL-констант в корпусе четыре. Формулировка ADR-017 §1 «ТРИ канала»
     как утверждение о корпусе некорректна и настоящим ADR корректируется. Текст ADR-017 не
     правится (append-only), в его строку статуса добавляется отметка о корректировке.
  2. Решение о целевом состоянии: канал определяется событием, а не документом-источником.
     `order_completed` — событие статус-канала независимо от того, какая подписка его
     породила. Константа `CRM_Webhook_URL_OrderCompleted` упраздняется; 1С-LM-02 отправляет
     на `CRM_Webhook_URL_OrderStatus`. Каналов остаётся три, как решение, а не как чтение.
     Задача 1С: строка конфигурации плюс строка реестра подписок, нулевая по логике.
     Оговорка `d5_t04@8a7eedbb:343` о намеренном разделении касается физлиц и юрлиц и к
     выбору URL не относится.
  3. Задача Bitrix-подрядчику не порождается: принимающий эндпоинт уже заказан и уже обязан
     обрабатывать `order_completed` (`d4_t03@8a7eedbb:602`).
  4. Канон §4 T2 дополняется явной строкой о двух подписках-источниках `order_completed`,
     чтобы читатель канона видел этот факт архитектуры.
  5. Причинность между двумя источниками текстом не установлена (К-7): не сказано, меняется
     ли статус «Заказа покупателя» при вызове /close_order для юрлица. Если меняется, оба
     события следуют из одного факта и второе глушится общей таблицей
     `b_dom_processed_1c_events` по ключу `(CRM_Deal_ID, event)` (ADR-015). Если нет,
     возможен разрыв по времени. Вопрос выносится в CQ-06 к List.kg, объединение с CQ-02 не
     производится.
  6. ADR-015 §2 (курсор `doc_version` отдельный на канал) для статус-канала остаётся
     нереализуемым до закрытия P-05: поля версии нет ни в одном из двух payload. Констатация,
     не новое решение.
  7. Процессное следствие: удаление блока «инвентарь исходящих событий» из брифа F5-02
     решением ADR-017 п.4 было преждевременным — именно этот шаг обнаружил бы четвёртую
     константу. Блок в брифе помечается снятым с указанием причины, но факт фиксируется.

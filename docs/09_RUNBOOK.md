# 09_RUNBOOK — как запускать сессии

**Статус:** LIVING · **Редакция:** rev1.1 · **Основание:** ADR-040 и ADR-041, пункт M1-06 плана `docs/08_METHOD_PLAN.md`

> Документ для Owner, не для сессии. Отвечает на один вопрос: что открыть и что написать,
> чтобы работа началась. Правила самих сессий живут в `docs/01_CONVENTIONS.md`,
> `docs/03_ROLES.md`, `docs/04_SESSION_PROTOCOL.md`, `CLAUDE.md` и в файлах `prompts/`.
>
> **Правило роста файла (ADR-040 §4).** Раздел появляется здесь только после того, как
> описываемая машинерия реально применена в репо. То, что запланировано, но не построено,
> перечислено в §6 отдельно, как «пока нельзя». Ранбук, описывающий несуществующую команду,
> считается дефектом файла.

## 0. Что открыть под задачу

| Что нужно | Кого запускаешь | Где | Модель |
|---|---|---|---|
| Решить, как должно быть для клиента и для денег: SLA, отмены, возвраты, тексты, приоритеты | **Business** | чат | Fable |
| Принять техническое решение, разобрать проблему, ревью регистра, поправить роудмап | **Architect, режим A** | чат | Opus |
| Получить бриф под следующую задачу | **Architect, режим B** | чат | Opus |
| Выполнить одну задачу по готовому брифу | **Executor** | Claude Code, если бриф в мандате пилота; иначе чат | Sonnet |
| Внести session-блок в репо и закоммитить | **Applier** | чат; Claude Code после гейта §4.1 | Sonnet |
| Проверить пакет перед отправкой подрядчику, фазу перед DONE, PROCESS-ADR перед апрувом | **Reviewer** | чат | Fable |

Штатная архитекторская сессия закрывает оба режима сразу: решения плюс брифы под следующие
задачи. Это дешевле по контексту, чем два чата.

## 1. Правило очерёдности

Порядок жёсткий, читать сверху вниз:

1. `bash tools/verify.sh` даёт RED — чиним первым делом, новые задачи не стартуют (К-9).
2. Есть session-блок, который ещё не внесён в репо — сначала Applier. Непринятый блок означает
   протухший `docs/00_STATE.md`, а на протухшем состоянии следующая сессия строит решения.
3. Только после этого новая сессия.

## 2. Признак пути и SHA

Путей два, и роль не имеет способа понять, куда её запустили, если ей не сказать.
Чатовая сессия читает репо по сети, сессия внутри Claude Code читает диск. Перепутанный
путь не отвергается сам собой: текст под Claude Code спокойно исполняется в чате и наоборот,
а обнаруживается это потом, по пустому диффу.

Поэтому каждое пусковое сообщение открывается строкой объявления пути (ADR-041 §1).
Строку не удалять.

SHA нужен только чатовому пути. Из любой папки внутри клона:

```
S=$(git log --format='%H' -1); echo "SHA сессии: $S"; echo "База: https://raw.githubusercontent.com/ilyasbazarov/dom-prorab-ecom-arch/$S/"
```

Хэш подставляется вместо `<SHA>`, обычно в трёх местах: ссылка на промт, «читай по SHA», база.
Замена делается поиском по строке, не глазами. Позже это заменит `tools/start.sh` (пункт M1-13).

Промт роли: открой в браузере ссылку из пускового сообщения, скопируй всё, вставь в чат
следующим блоком.

## 3. Чат-сессии

Порядок: пусковая строка → файл промта целиком → задача, бриф или session-блок.

```

Файл не открылся → стоп и запрос содержимого (К-17). Пиши человеческим языком (К-16). Anti-improvisation: гэп → CONTEXT GAP. Вопросы сессии: <…>
```

### 3.3 Architect, режим B (выпуск брифа)

Та же пусковая строка, задача формулируется так:

```
Задача сессии: выпусти бриф briefs/<ID>.md по docs/06_BRIEF_TEMPLATE.md под задачу <ID>. Перед брифом проверь, нет ли по этой задаче нерешённых ADR или открытых вопросов: поверх нерешённого бриф не генерится. Поле «Файлы на запись» заполни маркированным списком, один путь на строку, в обратных кавычках.
```

Для метод-сессии (волны M) добавь строкой:

```
Дополнительно к обязательному контексту роли прочитай https://raw.githubusercontent.com/ilyasbazarov/dom-prorab-ecom-arch/<SHA>/docs/08_METHOD_PLAN.md. Перед работой проверь гейт волны по плану; гейт не выполнен → стоп, доложи чего не хватает.
```

## 4. Claude Code

### 4.1 Гейт запуска, делается один раз

Из любой папки внутри клона:

```
cd "$(git rev-parse --show-toplevel)"
git status
git pull --rebase origin main
test -x .git/hooks/pre-commit || ln -s ../../tools/hooks/pre-commit .git/hooks/pre-commit
bash tools/hooks/selftest.sh
```

Нужны два результата: дерево чистое и «провалено 0». Любой другой исход самотеста означает
стоп: сломанная проверка хуже отсутствующей, потому что отказывает тихо.

Дальше открываешь в приложении папку клона целиком, не подпапку, и подтверждаешь доверие.
`CLAUDE.md` лежит в корне и подхватывается сам, ссылки на роли руками не прикладываются.

### 4.2 Режим «примени session-блок»

```
Ты внутри репозитория dom-prorab-ecom-arch, файлы читаешь с диска, curl и SHA не нужны. Диска у тебя нет — стоп, ты запущена не там.
Примени session-блок ниже. Роль Applier, правила — docs/04_SESSION_PROTOCOL.md, секция «Правила применения», за одним исключением: правь файлы напрямую инструментами Edit и Write. Требование выдать один bash-блок написано для чатового пути, где у модели нет диска; ты его не выполняешь.
Секцию FILE_PATCHES применяй как есть: каждый пункт несёт файл, тип операции и дословный контент (ADR-042).
Ничего не улучшай и не переформулируй. Пункты proposed вноси со статусом proposed и перечисли отдельно.
Отчитывайся только о том, что сделала сама. Пересказывать разделы входного блока как собственные действия запрещено.
Всё одним коммитом. git push не делай.
В конце — блок «НА АРХ-РЕВЬЮ»: все proposed, все открытые вопросы, все несоответствия. Нечего писать — напиши «нет» явно.
Session-блок: <вставить целиком>
```

### 4.3 Режим «исполни бриф»

```
Ты внутри репозитория dom-prorab-ecom-arch, файлы читаешь с диска, curl и SHA не нужны. Диска у тебя нет — стоп, ты запущена не там.
Исполни бриф briefs/<ID>.md. Роль Executor, полные правила — prompts/executor.md, законы — CLAUDE.md. Мандат — ровно этот бриф, шаги за его пределами не исполняешь. SHA сессии = git rev-parse HEAD, цитаты — файл@SHA:строки. Не-идемпотентное и всё, что отнесено к классу B, — только после моего явного подтверждения. Done — только по критериям приёмки брифа. В конце session-блок в описании коммита; git push не делай.
```

Мандат пилота — ровно эти два режима (ADR-029 §2). Пилотный бриф назван: `F5-01`.
Любая другая задача внутри Claude Code требует нового ADR.

**Что делаешь ты и никогда не сессия** (ADR-034 §2): `git push`; все апрувы, включая развилки,
proposed и подмену живых конфигураций; постановка задач.

Пока сессия работает, не вмешивайся. Остановилась с вопросом — отвечай, но тогда в журнальной
строке в колонке «возврат» пишется причина, а не «нет»: `ADR-034 §3` считает это инцидентом
исполнения, а не рабочим вариантом.

### 4.4 После коммита

```
bash tools/verify.sh
git log --format='%H' -1
git push origin main
```

## 5. Если пошло не так

**Сессия остановилась и задаёт вопрос.** Штатное поведение всех ролей. Отвечай по существу и не
подсказывай нужный ответ: остановка обычно означает реальное расхождение в репо.

**`CONTEXT GAP`.** Сессии не хватает файла или значения. Дай содержимое в чат либо согласись
завести discovery-бриф. Не отвечай «делай как считаешь нужным».

**Роль отчиталась о действиях, которых на её пути не бывает** (чатовая говорит про git и диск,
CC-сессия про curl и SHA). Проверь, куда вставлено пусковое сообщение, и сверь результат с репо
счётчиками, а не с её отчётом (ADR-041 §4).

**Хук завалил коммит.** В тексте названа конкретная проверка. Обход (`--no-verify` или любой
аналог) допускается только по К-24: одновременно три строки в `docs/00_STATE.md` — причина, что
осталось непроверенным, срок починки. Нет любой из трёх — обход запрещён, работа откладывается.

**`verify.sh` даёт RED.** Следующая сессия начинается с починки, новые задачи не стартуют (К-9).

**Applier выдал скрипт с `git push origin main` внутри.** Это остаток прежней редакции
`prompts/applier.md` §Формат выхода п.3. `ADR-036 §5` убирает его пачкой A; до применения пачки
строку вырезаешь сам либо оставляешь осознанно.

**Дерево грязное на старте сессии Claude Code.** Стоп. Не работать поверх чужих правок.

**Сессия предлагает применить решение со статусом `proposed`.** Нельзя без твоего явного
апрува (К-15). Апрув меняет одну строку статуса, не текст решения.

## 6. Чего сейчас нельзя, и когда станет можно

| Хочется | Почему нельзя сейчас | Когда открывается |
|---|---|---|
| Запустить две пишущие сессии одновременно | нет буфера и сборщика: два блока на одну строку STATE затирают друг друга, drop-in-патчи дрейфуют по SHA | порядок ADR-037 §2: волна M1 → success-критерий пилота (ADR-034) → буфер, сборщик, деревья, две проверки → проверочный прогон одной задачи → две дорожки |
| Отдельное рабочее дерево на сессию (`git worktree`) | не заведено | пункт M2-02 |
| Скрипт «чисто ли, можно ли стартовать» | не написан | пункт M2-03 (`tools/session_status.sh`) |
| Машинная проверка пары задач на параллелимость | не написана | пункт M2-04 (`tools/parallel_check.sh`) |
| Отдельная роль «генератор брифов» | брифы выпускает Architect в режиме B | пункт M2-06 |
| Пусковое сообщение с уже подставленным SHA и признаком пути | не написан | пункт M1-13 (`tools/start.sh`) |
| Дать Claude Code задачу вне двух режимов §4 | мандат ADR-029 §2 | только новым ADR |

Статусы пунктов смотри в `docs/08_METHOD_PLAN.md`, там же гейты волн.

## 7. Шпаргалка

| Действие | Команда |
|---|---|
| SHA и база для чат-сессии | `S=$(git log --format='%H' -1); echo "SHA сессии: $S"` |
| Поставить хук и проверить его | `ln -s ../../tools/hooks/pre-commit .git/hooks/pre-commit` затем `bash tools/hooks/selftest.sh` |
| Гейт целостности после apply-коммита | `bash tools/verify.sh` |
| Санкционированная правка immutable-зоны | `ALLOW_RAW_CHANGE=1 bash tools/verify.sh` |
| Выложить наверх | `git push origin main` — только Owner, отдельной командой |

## 8. Что в этом документе не проверено

Механизм агентов Claude Code (`.claude/agents/`) в репо заведён частично: есть `executor.md`,
файла `architect.md` нет. Пусковые сообщения §4.2 и §4.3 работают без агентов и являются
основным способом. Первый прогон пилота закрывает эту проверку.

# 04_SESSION_PROTOCOL — Жизненный цикл сессий и session-блок

**Статус:** STABLE (изменения через ADR). Основание: ADR-007.

## Типы сессий
| Тип | Промт | Выход |
|---|---|---|
| Business | `prompts/business.md` | решения `[BUSINESS]` + session-блок |
| Architect (режим A: решения/ревью/роудмап) | `prompts/architect.md` | ADR + патчи + session-блок |
| Architect (режим B: брифы) | `prompts/architect.md` | `briefs/<ID>.md` + session-блок |
| Executor | бриф + `prompts/executor.md` | артефакт задачи + session-блок |
| Applier (чатовый путь) | `prompts/applier.md` | ОДИН commit-скрипт (К-6) |
| Reviewer (ревью целостности) | `prompts/reviewer.md` | список находок + session-блок |
| Claude Code · применение (Applier) | `CLAUDE.md` (авто) + session-блок от Owner | правки файлов + локальный коммит (session-блок в описании) + блок «НА АРХ-РЕВЬЮ» |
| Claude Code · исполнение брифа (Executor) | `CLAUDE.md` (авто) + `briefs/<ID>.md` (мандат — ADR-049 §1) | артефакт по return-this + session-блок + локальный коммит |
| Claude Code · Architect режим A (решения/ревью/роудмап) | `CLAUDE.md` (авто) + `prompts/architect.md` (мандат — ADR-049 §1) | ADR + FILE_PATCHES + session-блок + локальный коммит |
| Claude Code · Architect режим B (брифы) | `CLAUDE.md` (авто) + `prompts/architect.md` (мандат — ADR-059 §1) | `briefs/<ID>.md` + session-блок + локальный коммит |
| Claude Code · Reviewer (ревью целостности) | `CLAUDE.md` (авто) + `prompts/reviewer.md` (мандат — ADR-049 §1) | список находок + session-блок + локальный коммит |
| Claude Code · Business (бизнес-решения) | `CLAUDE.md` (авто) + `prompts/business.md` (мандат — ADR-059 §1) | решения `[BUSINESS]` + session-блок + локальный коммит |

Штатная архитекторская сессия завершается пакетом «решения + патч роудмапа + брифы под следующие задачи» — два режима в одной сессии допустимы и предпочтительны (экономия загрузки контекста). Развилки Owner при этом всегда подаются отдельным блоком по К-25 (суть выбора, варианты с последствиями, рекомендация отдельной строкой), не внутри тел решений (ADR-030 §2).

**Путь по умолчанию (ADR-124, решение Owner 2026-08-11).** Все шесть ролей запускаются в Claude Code. Строки таблицы про чатовый путь остаются действующими, но описывают АВАРИЙНЫЙ ход: машинной проверки ответа там нет, и пусковая строка это объявляет.

**Где живёт машинная часть (ADR-122 §4).** На пути Claude Code роль применяет правки сама, а session-блок кладёт в описание коммита — поэтому в чат машинная часть НЕ печатается: в чате остаётся только текст к Owner по К-39 и К-42. На чатовом пути правило противоположное и не меняется: весь выход идёт одной вставкой (ADR-042 §3), потому что машинную часть переносит Owner руками и без печати она не существует. Разграничение по пути исполнения — то же, что у выхода Applier (ADR-043 §2).

## Ритуал старта (любая роль)
0. Проверить признак пути ДО чтения обязательного контекста (ADR-041 §2). Первая строка пускового сообщения объявляет путь и несёт утвердительную проверку (ADR-045 §1-§2): роль первым действием выполняет `git rev-parse HEAD`. Чатовый путь — команда отработала и вернула хэш → стоп, роль запущена не там, доклад Owner, обязательный контекст не читать. Путь Claude Code — команда не отработала или хэш не вернулся → стоп, роль запущена не там. Несовпадение есть стоп и вопрос Owner, а не адаптация под фактическую среду. Затем предъявить предмет сессии: пусковое сообщение несёт SHA коммита, которым предмет применён, и адреса вида `файл:строки`; не нашёлся хотя бы один адрес → стоп и доклад Owner (ADR-048 §1-§2). Первая строка отчёта роли — дословный вывод команды проверки признака пути и перечень предъявленных адресов; пересказ отчётом не является (ADR-048 §3, К-36, К-28).
1. Получить от Owner строку `SHA сессии: <хэш>`. SHA нет → запросить, `main` не читать.
2. Загрузить обязательный контекст роли (см. `03_ROLES`) — только curl по SHA, каждый файл полным raw-URL (К-18).
3. Хотя бы один файл не открылся → СТОП немедленно (К-17): назвать путь и URL, попросить Owner прислать содержимое в чат. Не продолжать по остальным файлам, не делать выводов об отсутствии (К-14).
4. Переформулировать задачу своими словами, перечислить полученные входы.
5. Неполнота → `CONTEXT GAP: <что отсутствует и почему нельзя продолжать>`. Стоп, не догадка.

## Ритуал конца: session-блок (без него сессия не закрыта, знание потеряно)

```
=== SESSION LOG · <дата> · <тип/ID> ===

## SESSION_LOG   (→ sessions/<дата>_<id>.md)
- Задача: ...  - Сделано: ...  - Отклонения: <или "нет">

## STATE_PATCH   (→ docs/00_STATE.md)
- Фаза/задача: <старый статус> → <новый>
- Стенд-ап: <прошлый шаг · где мы · следующий шаг · своей дорожкой · на Owner лично>. ID (OQ/BQ/CQ/P/ADR) из заменяемых строк либо сохраняются в новом тексте, либо называются в «В архив дословно»
- Подробности для модели: <ТОЛЬКО append в конец секции ЛИБО адресная правка «заменяемый текст дословно → новый текст дословно». Замена секции целиком запрещена>
- В архив дословно: <строки, полностью закрытые этой сессией, дословно — переносятся в docs/00_STATE_ARCHIVE.md тем же коммитом (К-19); или "нет". Подпункт обязателен>
- Новые открытые вопросы / блокеры: <или "нет">

## NEW_DECISIONS (→ append docs/02_ADR_LOG.md; "нет" если нет)
- ADR-0XX [BUSINESS|ARCH|PROCESS]: <заголовок>
  Контекст · Решение · Последствия (полный blast radius: файл/§; КАЖДЫЙ пункт несёт маркер
  времени из закрытого перечня ADR-044 §1: [сейчас] · [пачкой A] / [пачкой B] ·
  [задачей <ID>] / [задачами волны <ID>] · [отдельным коммитом] · [без правок].
  Пункт без маркера — гэп, форма вне перечня приравнивается к отсутствию маркера)
  Статус: accepted | proposed

## REGISTER_PATCHES (→ l2-registers/*; "нет" если нет)
- <файл регистра>: <операция: добавить запись / сменить статус P-xx / закрыть вопрос> + дословный контент

## FILE_PATCHES  (→ любой файл репо вне STATE, ADR-лога, регистров и журнала; "нет" если нет)
- <путь файла> · <операция: новый файл / замена / append / удаление строки> · <точное место: дословный якорь поиска из текущего текста файла> + дословный новый контент

## NEW_CONVENTIONS (→ docs/01_CONVENTIONS.md; по умолчанию proposed)

## JOURNAL_ROW   (→ append sessions/JOURNAL.md; ADR-031, обязательна)
| <дата> | <id сессии> | <тип> | <тема> | <тип артефакта> | <бюджет или —> | <факт заходов> | <возврат: нет / причина> | <критик: пройден / обойдён (STATE) / не требуется> | <контекст, знаки, или —> | <модель> | <блокирует: продуктовый шаг, который без этой сессии встал; продуктовая сессия пишет «Служит: Ф-x»> |

=== END SESSION ===
```

Отличие от базиса holika: добавлена секция `REGISTER_PATCHES` — в этом проекте регистры (Problem, Contractor Questions, Open Questions, Assumptions) — основной рабочий продукт.

## Правила применения (для Applier)
- `STATE_PATCH` — применяется всегда. `NEW_DECISIONS` — вносятся ВСЕ, включая `proposed` (К-15): номер ADR = следующий по факту в файле, не из блока; статус переносится из блока дословно. `proposed` дополнительно выводится списком «требует апрува Owner».
- `NEW_CONVENTIONS` — вносятся всегда; без явного «одобряю» от Owner — с префиксом `[proposed]` (К-15).
- Апрув `proposed` — правка одной строки статуса; допустимость по verify — ADR-016. До его реализации proposed-ADR не выпускаются.
- ADR-лог и регистры — append/статусные правки; существующие записи не переписываются (P-xx меняет статус, не текст доказательств — новые доказательства добавляются).
- `FILE_PATCHES` — применяется всегда. Правки любого файла репо вне STATE, ADR-лога, регистров и журнала идут ТОЛЬКО через эту секцию (ADR-042 §2). Патч, выложенный прозой вне session-блока, считается невыпущенным: Applier его не видит и не применяет. Ссылка внутри блока на текст вне блока («см. патч выше») — дефект блока, блок возвращается автору (ADR-042 §3).
- Пункт блока последствий без маркера времени — гэп (ADR-044 §2): Applier на нём не останавливается, а выносит пункт строкой в блок «НА АРХ-РЕВЬЮ». Форма вне закрытого перечня ADR-044 §1 трактуется как отсутствие маркера.
- Патч ссылается на несуществующую структуру → `СТРУКТУРНОЕ НЕСООТВЕТСТВИЕ`, стоп.
- Applier не пишет ни в один файл содержимое, отсутствующее в session-блоке, ни при каких срабатываниях гейта. Сработала проверка — блок возвращается автору с дословным выводом проверки. В частности при срабатывании проверки 5 (исчезли ID → 00_STATE_ARCHIVE.md) Applier НЕ сочиняет архивную строку: исчезновение ID означает либо потерю содержимого, либо незаявленное закрытие, и различает их автор блока, а не применяющий.
- В `docs/00_STATE_ARCHIVE.md` переносится только текст из подпункта «В архив дословно» STATE_PATCH. Пересказ и пометка «дословно» без предъявленного источника запрещены.
- Выход Applier зависит от пути исполнения (ADR-043 §2). Чатовый путь: ОДИН bash-блок (К-6) — записывает файлы, `git add -A && git commit && git log --format='%H' -1`. Путь Claude Code: прямые правки файлов инструментами Edit и Write плюс локальный коммит, bash-блок не выдаётся. На обоих путях роль не делает `git push`: его выполняет Owner отдельной командой (ADR-036 §5).
- После применения Applier ОБЯЗАН выдать блок **«НА АРХ-РЕВЬЮ»** (на обоих путях): все proposed-пункты, все открытые вопросы и все несоответствия, встреченные при применении, одним списком с указанием файла и сути. Пустой блок пишется явно («нет»). Сушить вопросы запрещено: Architect не должен догадываться, что осталось незакрытым.
- `JOURNAL_ROW` аппендится в sessions/JOURNAL.md тем же коммитом. Секции нет → дефект session-блока, блок возвращается автору, применение не выполняется.

## Правило явного патча (для Business/Architect/Executor)
Адресат патча не видит твой thinking. Каждый патч — drop-in: точный файл, точное место, тип операции (вставка/замена/append/новый файл), дословный контент. Ссылки «по аналогии» запрещены. В конце сессии — сводка «файл → операция».

## Гейт целостности
После каждого apply-коммита Owner запускает `bash tools/verify.sh`. RED → следующая сессия начинается с починки, новые задачи не стартуют.

Для Claude Code-сессий гейт исполняется pre-commit хуком ДО коммита (ADR-028): на старте сессии — `bash tools/hooks/selftest.sh` с ожиданием «провалено 0»; `git commit --no-verify` — только по явному апруву Owner с фиксацией в session-блоке. К-9 (verify после коммита) остаётся обязанностью Owner для чатового пути на переходный период.

Обход гейта (любой аналог `--no-verify`) — только по К-24: одновременная строка в docs/00_STATE.md с причиной, перечнем непроверенного и сроком починки. Нет всех трёх — обход запрещён (ADR-033).

## Definition of Done
- Executor-задача: артефакт принят по критериям брифа + session-блок применён + verify GREEN. Для скриптовых задач — только после подтверждённого Owner лога реального прогона.
- Architect-сессия: все поднятые вопросы либо решены (ADR), либо явно в Open Questions с владельцем.
- Business-сессия: каждая развилка закрыта решением или явным DEFER с датой возврата.
- Reviewer-сессия: каждая находка имеет уровень, цитату и адресата; в конце — однозначный вывод «отправлять можно / нельзя».
- Пакет подрядчику: отправка допускается только после Reviewer-сессии без незакрытых находок уровня STOP (ADR-024).

## Доступ (жёстко, из holika-базиса)
Только `curl` по commit-SHA: `https://raw.githubusercontent.com/ilyasbazarov/dom-prorab-ecom-arch/<SHA>/<путь>`. Web-fetch/браузер запрещён (кэш). Двойной слэш → HTTP 400. api.github.com без авторизации лимитируется — SHA даёт Owner (он у него всегда в буфере: apply-скрипт печатает его последней строкой).

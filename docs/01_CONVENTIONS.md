# CONVENTIONS

- **К-1. Доказательность.** Ни один вывод не имеет статуса CONFIRMED без цитаты из L3-снапшота с прямым побайтовым доступом (SHA + файл + строки). Пересказы третьих лиц доказательством не являются.
- **К-2. Приоритет канона.** Конфликт L0 vs L3 трактуется как дефект документации подрядчика. Изменение L0 — только через ADR.
- **К-3. Immutable снапшоты.** L3-файлы после коммита не редактируются. Новая версия документа = новый файл с датой. Diff строится машинно от снапшота.
- **К-4. Минимальная достаточность.** Артефакты (Knowledge Graph, Bounded Context Map и пр.) вводятся только при доказанной необходимости, не «по лучшим практикам».
- **К-5. Протокол KB.** Из Master KB без подтверждения используются только секции [1], [2], [9]. Остальное — тезис агента → явное подтверждение/корректировка владельца в сессии.
- **К-6. Скрипты.** Все скрипты — единый copy-paste-ready bash-блок без ручных плейсхолдеров. Каждое значение, известное из контекста сессии, репо, брифа или памяти проекта (пути, SHA, имена файлов, ID, пороги, адреса), подставляется в скрипт литерально. Значение неизвестно → `CONTEXT GAP` и стоп; плейсхолдер вместо значения запрещён. Единственное исключение — launch-строки промтов: SHA сессии подставляет Owner в момент запуска, слот `<SHA>` помечен явно.
- **К-7. Оракул 1С.** Статусы подтверждения: CONFIRMED-DOC (видно в тексте ТЗ) / CONFIRMED-FACT (подтверждено List.kg). Отсутствие в ТЗ = «подрядчик не обязан», а не «система так не делает».

- **К-8. Session-блок обязателен.** Любая сессия (Business/Architect/Executor) закрывается одним session-блоком по 04_SESSION_PROTOCOL. Незакрытая сессия = потерянное знание.
- **К-9. Verify-гейт.** После каждого apply-коммита Owner запускает `bash tools/verify.sh`. RED → следующая сессия начинается с починки; новые задачи не стартуют.
- **К-10. SHA сессии.** Агент работает только по commit-SHA, приложенному Owner. SHA не приложен → агент обязан запросить, чтение main запрещено.
- **К-11. Только клон.** Правки и загрузки в репо — только через локальный клон и apply-скрипты. Веб-интерфейс GitHub для изменений запрещён: создаёт расходящиеся истории (инцидент 2026-07-18).
- **К-12. Санкционированные исключения verify.** Изменение immutable-зоны допускается только при явном решении в сессии; verify для такого коммита запускается как `ALLOW_RAW_CHANGE=1 bash tools/verify.sh`. Категории «ожидаемый RED» не существует: либо GREEN, либо починка.
- **К-13.** — номер аннулирован (ADR-014). Конвенция под этим номером была предложена в сессии
  `arch_phase5_waves_briefs` (2026-07-23) и утрачена вместе с чатом; восстановлению не подлежит.
  Номер не переиспользуется.
- **К-14. Недоступность ≠ отсутствие.** HTTP 404 по угаданному пути, лимит API, ошибка сети и любой
  другой отказ доступа означают «не установлено», а не «файла нет». Вывод об отсутствии артефакта
  допускается ТОЛЬКО из авторитетного листинга (`git ls-tree` от Owner) или из документа, который
  обязан его перечислять. Косвенный вывод об отсутствии не может служить основанием ADR, приоритета
  или задачи; при недоступности — `CONTEXT GAP` и запрос листинга. Основание: инцидент 2026-07-23
  (OQ-05), ADR-014.
- **К-15. Предложенное коммитится.** Proposed-решение вносится в целевой файл в том же apply-коммите
  со статусом `proposed` (ADR — `**Статус:** proposed`; конвенция — префикс `[proposed]`), а не
  выводится списком в чат. Апрув Owner меняет только строку статуса (механика — ADR-016). Ни одно
  решение проекта не существует вне репо. Основание: ADR-014.
- **К-16. Человеческий язык.** Главное правило любой роли и любой сессии, выше остальных дисциплин по приоритету изложения. Пиши так, чтобы уставший человек понял с первого прохода: короткие предложения, обычные слова, без внутреннего жаргона ролей, фаз и режимов. Порядок подачи: что нужно от Owner → какие есть варианты → какой лучше и почему. Рекомендация по развилке выносится отдельной строкой, а не прячется в конце абзаца. Проектные термины (P-xx, ADR-xxx, К-x, L0–L3, BQ/OQ) употреблять можно, но при первом появлении в ответе пояснять одной фразой. Формулировка, которую нужно перечитывать дважды, считается дефектом ответа независимо от её точности.
- **К-17. Стоп при недоступности файла.** Если хотя бы один файл из обязательного контекста роли или из Context-to-load брифа не открылся (404, лимит API, ошибка сети, пустой ответ) — сессия останавливается немедленно. Агент называет точный путь, точный URL, по которому пробовал, и просит Owner прислать содержимое файла в чат. Продолжать «по остальным файлам» и достраивать картину запрещено; вывод об отсутствии файла тоже запрещён (К-14). Работа возобновляется только после того, как Owner прислал содержимое либо явным решением снял файл с обязательного списка.
- **К-18. Ссылка на файл — литеральный raw-URL.** Голый путь (`prompts/architect.md`, `docs/00_STATE.md`) инструкцией на чтение не является: агент не находит его локально и уходит искать в поисковике. Любой файл, который агент обязан прочитать, указывается полным URL вида `https://raw.githubusercontent.com/ilyasbazarov/dom-prorab-ecom-arch/<SHA сессии>/<путь>`. Путь без URL допустим только как ссылка для человека. Ссылки вида `github.com/.../blob/...` запрещены: это HTML-страница, а не файл, и она обычно пиннится к чужому SHA.- **К-19. Контекстная диета и синхронизация.** В обязательный контекст ролей входит docs/02_ADR_INDEX.md вместо полного docs/02_ADR_LOG.md; полный текст конкретного ADR поднимается точечно по номеру. Каждый append ADR в лог сопровождается строкой индекса ТЕМ ЖЕ коммитом. docs/00_STATE.md держит только открытое (open / DEFER / в работе); полностью закрытая строка переносится в docs/00_STATE_ARCHIVE.md дословно тем же коммитом. Архив и полный лог читаются точечно по ID. Основание: ADR-027; базис — holika ADR-064 @ c229bb7.
  Переиздана ADR-137: у КАЖДОГО раздела docs/00_STATE.md есть правило выхода и машинный лимит, а
  не только у стенд-апа. Шапка — не более 2500 байт целиком, до §Текущий фокус (лимит одной
  строки `**Версия:` ловил только её, и рядом жил хвост прежней шапки на 22 360 байт).
  §Подробности для модели — ИНДЕКС, не хранилище: строка на сессию «дата · сессия · предмет ·
  носитель», не более 150 непустых строк; содержание живёт в sessions/, docs/02_ADR_LOG.md и
  docs/00_STATE_ARCHIVE.md. §Открытые вопросы — указатели, не более 15 непустых строк: учётную
  строку с владельцем и признаком закрытия ведёт l2-registers/open_questions.md, наблюдение о
  методе без владельца — docs/10_SCARS.md. Правило выхода, а не разовая чистка: раздел без
  машинного лимита не отдаёт содержимое никогда — замер 2026-08-12 дал 97% файла в трёх кусках
  без правила при 0.7% у стенд-апа, где правило есть (`reference/2026-08-12_state_weight_measure.md`).
- **К-20. FILE-строка.** Первая строка каждого docs/NN_*.md и CLAUDE.md — литеральная `# FILE: <путь от корня>`. Агент при чтении сверяет её с тем, что открывал; несовпадение = `СОДЕРЖИМОЕ НЕ ТО: <файл>` и стоп. Проверяется pre-commit хуком. Основание: ADR-027; базис — holika ADR-054.
- **К-21. Claude Code-сессии.** Внутри Claude Code репо читается с локального диска; SHA сессии фиксируется `git rev-parse HEAD` и используется в цитатах файл@SHA:строки. Старт — по CLAUDE.md (чистое дерево, обязательный контекст, самотест хука до первого коммита). Session-блок кладётся в описание коммита. `git push` — только по явной команде Owner. К-10 и К-18 остаются законами чат-сессий и на Claude Code-сессии не распространяются. Основание: ADR-029.
- **К-22. Вывод без артефакта не существует.** Любой замер, листинг, выгрузка или численный вывод, на который опирается решение, кладётся файлом в репо той же сессией: сырьё — `reference/`, брифы — `briefs/`, решения — журнал решений. В docs/00_STATE.md число упоминается только со ссылкой на файл; голая цифра без ссылки — незакрытая задача. Основание: ADR-032.
- **К-23. Аномалия заводится строкой немедленно.** Любое необъяснённое поведение системы — строка с владельцем в момент обнаружения; носитель переиздан ADR-138 §1 вслед за ADR-137 §3: аномалия с адресатом и признаком закрытия идёт в l2-registers/open_questions.md, наблюдение о методе без владельца — в docs/10_SCARS.md номером Ш-NN. В §Открытые вопросы docs/00_STATE.md строка НЕ заводится: раздел держит указатели и ограничен пятнадцатью строками. Прежняя редакция правила называла носителем именно его — и именно поэтому там скопилось семьдесят шесть пунктов, из которых семьдесят закрыть было нечем, независимо от влияния на результат и от того, устранено ли следствие. Закрытие — только по установленной причине либо явным решением Owner «принимаем риск» (тоже фиксируется). Фиксация в коммит-сообщении фиксацией не считается. Основание: ADR-032.
- **К-24. Протокол снятия гейта.** Обход гейта целостности (`--no-verify` и любой аналог) допускается только при одновременной записи в docs/00_STATE.md трёх полей: причина; что осталось непроверенным; срок починки. Нет любого из трёх — обход запрещён, работа откладывается. Основание: ADR-033.
- **К-25. Развилки — отдельным документом.** Развилки Owner подаются отдельным коротким блоком: заголовок, суть выбора, варианты с последствиями, рекомендация отдельной строкой; ответ на развилку не должен требовать чтения ADR целиком. Внутри тела решения развилки не подаются. Основание: ADR-030 §2.
- **К-26. Детерминированное — коду.** Разбор структуры, подсчёт, сверка хешей, проверка формата исполняются скриптом, не моделью; модель применяется там, где нужно суждение. Основание: ADR-030 §5.
- **К-27. Отменяющее решение проверяется сплошным поиском.** Решение, отменяющее или
  переопределяющее понятие (а не двигающее значение), применяется не только по перечисленным
  якорям. Исполнитель прогоняет сплошной поиск понятия по репо, печатает совпавшие строки с
  номерами и вносит в blast radius вердикт по КАЖДОМУ совпадению: «правится» либо «остаётся,
  потому что». Пустая выдача поиска фактом не является. Форма команды поиска задаётся К-35;
  аттестация предъявляет команду дословно. Основание: инцидент ADR-012 → ADR-019/ADR-020.
- **К-28. Критерий формулируется утвердительно и числом.** Не «вывода нет», а «файлов
  кроме заглушки: 0». Пустой вывод результатом не является никогда. Скрипт, выносящий вердикт,
  печатает совпавшие строки с номерами, а не метку PASS/FAIL: метка непроверяема, строки
  проверяемы. Дополняет К-22 и К-26.
- **К-29. Датировка расщеплена.** Имена сессий, брифов и артефактов датируются локальной
  датой. Любой временной ФАКТ в тексте документа пишется в UTC с явным суффиксом Z. Смешение
  даёт уверенные ложные выводы о таймингах прогонов и вебхуков.
- **К-30. Внешний факт существует только записью.** Ответ подрядчика или List.kg,
  полученный голосом, звонком или в мессенджере, фактом не является, пока не внесён в
  l2-registers/contractor_questions.md с датой, автором и дословной цитатой. Статус CONFIRMED-FACT
  (К-7) присваивается только такой записи. Пересказ в сессии доказательством не является (К-1).
- **К-31. Декомпозиция даёт непересекающиеся наборы.** Брифы, предназначенные к
  параллельному исполнению, выпускаются с непересекающимися наборами файлов на запись.
  Пересечение — дефект декомпозиции, а не повод запускать по одной. Поле «Файлы на запись»
  обязательно и машиночитаемо: заголовок, затем маркированный список, путь первым токеном
  строки. Поле отсутствует или пусто — отказ проверки, а не разрешение.
- **К-32. Приёмка формулы предъявляет разницу до прогона.** Формулируя приёмку правки
  формулы или алгоритма, выпиши обе формулы и предъяви разницу ДО прогона. Ненулевая разница
  входит в приёмку как ожидаемая величина, а не как условие «не изменилось».
- **К-33. Снимки в reference/ не правятся.** Файл, положенный в reference/ как снимок
  внешнего источника или как разбор, после коммита не редактируется. Исправление или новая
  редакция — новый файл с новой датой в имени. Провенанс снимка (строки, байты, sha256 первые
  16 символов) записывается в шапку разбора. Мотив тот же, что у К-3 для l3-external: снимок,
  правимый задним числом, ссылаться на себя не позволяет.
- **К-34. Признак правила-останова проверяется негативным прогоном.** Если смысл
  правила — остановить работу при наступлении условия X, его признак исполнения формулируется
  по ветке останова и проверяется намеренным прогоном при наступившем X. Положительная ветка
  («работа пошла, X не наступило») признаком не является: она наступает всегда и не
  удостоверяет ничего. Результат негативного прогона кладётся файлом (К-22); без файла
  признак не считается проверенным. Исход «роль назвала нарушение и продолжила работу»
  засчитывается как провал прогона, а не как частичный успех. Основание: ADR-046; поводы —
  ADR-041 и ADR-045, чьи признаки описывали положительную ветку, отчего правило трижды не
  сработало в поле.
- **К-35. Сплошной поиск выполняется в UTF-8 локали.** Поиск по К-27 и любой
  другой поиск по кириллическим понятиям выполняется командой с явным присваиванием локали в
  строке вызова: `LC_ALL=ru_RU.UTF-8 git grep -n -i "<понятие>" <SHA> -- ':!l3-external'`.
  Под байтовой локалью (`LC_CTYPE=C`) регистр кириллицы не сворачивается и выдача занижается
  молча: замер 2026-08-01 дал 4 совпадения против 31 на одном и том же запросе. Явный класс
  регистра вида `(П|п)` заменой не является: он закрывает только первую букву и на понятиях,
  встречающихся прописными, занижает так же (замер: «шрам» 4 против 27). Аттестация
  предъявляет команду дословно вместе с числом совпадений, чтобы форма сопоставления была
  проверяема, а не только её результат. Основание: ADR-047; образец реализации —
  `tools/hooks/selftest.sh:10-14`.

- **К-36. Пусковое сообщение называет предмет; роль предъявляет его и печатает
  вывод проверки.** Пусковое сообщение несёт SHA коммита, которым предмет применён (не SHA
  сессии-автора), и адреса предмета вида `файл:строки`. Роль первым действием — после проверки
  признака пути и до чтения обязательного контекста — предъявляет эти адреса с указанного SHA;
  не найдено хотя бы одно, значит стоп и доклад Owner. Отчёт роли открывается дословным
  выводом команды, которой роль проверяла признак пути, и перечнем предъявленных адресов;
  на пути Claude Code этот вывод стоит сразу после шапки К-39, потому что шапка идёт первой
  (К-39 §1, ADR-122 §2) — порядок двух правил разведён, требование предъявить вывод дословно
  не ослаблено.
  Пересказ («признак сошёлся», «предмет на месте») отчётом не является: метка непроверяема,
  строки проверяемы (К-28), а пересказ входного блока неотличим от отчёта о собственных
  действиях (docs/00_STATE.md:61). Основание: ADR-048; поводы — отставание SHA на коммит у
  Reviewer-сессии 2026-08-01 и пять случаев «назвала стоп-условие и продолжила».

- **К-37. Гейт не удовлетворяется изготовлением артефакта.** Роль, применяющая
  чужой session-блок, не создаёт содержимое, которого в блоке нет, ради прохождения проверки.
  Проверка, требующая артефакт, при его отсутствии в блоке даёт возврат блока автору с
  дословным выводом проверки. Вывод проверки фактурой не является (К-1): решение по
  срабатыванию принимается после чтения затронутых файлов. Основание: ADR-057.

- **К-38.** — номер аннулирован (ADR-074). Конвенция требовала расшифровки каждого кода
  проекта в тексте к Owner и блока самопроверки последним блоком ответа. Отменена по
  требованию Owner 2026-08-03: правило било по кодам, а тяжесть текста создают объём и
  структура; хвостовой блок не читается и расходует токены. Замена — К-39. Номер не
  переиспользуется.

- **К-39. Форма ответа роли: шапка, тезисы, лимит.** Введена ADR-074, заменяет К-38;
  переиздана ADR-122 (пункты 1, 2, 7, 8), ADR-123 (пункты 2, 6, 8, 9) и ADR-125 (пункты 8, 9).
  Все четыре записи `accepted`; префикс `[proposed]` снят апрувом Owner 2026-08-11.
  1. Ответ начинается шапкой из трёх строк: `Сделано:` · `Нужно от Owner:` · `Рекомендация:`.
     Каждая — ровно одна строка. Нечего написать — пишется «нет». Шапка идёт ПЕРВОЙ, до
     любого другого вывода: отчёт К-36 о признаке пути и предъявленных адресах ставится
     сразу после неё, а не перед ней.
  2. Текст к Owner после шапки — не более 25 непустых строк. Каждый блок развилки по К-25
     добавляет к лимиту 12 строк, развилок в одном ответе не более двух: решение Owner требует
     вариантов и последствий, и сжимать его до тезиса — потеря существенного, а третья развилка
     означает, что сессию надо делить. Не влезло — лишнее уходит в машинную часть, в файл репо
     или в следующую сессию. Лимит — сигнал о декомпозиции, а не повод сокращать существенное
     молча: выброшенное называется одной строкой.
  3. Форма — тезис плюс одна поясняющая фраза. Абзацев длиннее трёх строк нет.
  4. Коды проекта (ADR-xxx, К-x, P-xx, BQ/OQ/CQ, M<волна>-<NN>, Ф-x, L0–L3, имена задач и
     пачек) употребляются как есть. Расшифровывается только понятие, вводимое в проекте
     впервые, и один раз.
  5. Блока самопроверки нет. Никаких хвостовых блоков после машинной части.
  6. Развилки подаются по К-25; рекомендация дублируется третьей строкой шапки. Блок развилки
     открывается строкой вида `Развилка Р-<n>. <суть выбора>` — по ней же его опознаёт проверка
     и расширяет лимит пункта 2.
  7. На пути Claude Code машинная часть в чат НЕ печатается: её носители — файлы репо и
     описание коммита, роль применяет правки сама. В чате остаётся только текст к Owner.
     На чатовом пути ADR-042 §3 (весь выход одной вставкой) не меняется: там машинную
     часть переносит Owner, и без печати её не существует.
  8. Форма проверяется машинно — `tools/hooks/answer_check.sh` хуком `Stop` (ADR-122 §3).
     Возвращают ответ на переписывание пункты 1, 2, 3, 6, 7, непустота рекомендации и два
     грубых класса К-42; ещё два класса К-42 предупреждают, не возвращая (ADR-125 §1).
     Остальное машине не поддаётся и остаётся дисциплиной роли. Проверка не возвращает
     ответ за содержание, предписанное другим принятым правилом: обнаружился такой признак —
     он переводится в предупредительный слой, а не обкладывается исключениями (ADR-125 §1).
  9. Каждое срабатывание проверки кодируется (`ФОРМА-n`, `УПАКОВКА-n`) и копится в
     `.claude/answer_check.log`; свод — `bash tools/answer_stats.sh`. Второй проход по тому же
     ответу тоже меряется и помечается `ПОВТОР-`: замер обязан показывать исход возврата, а не
     только его факт, иначе правило-останов удостоверено первой веткой и вопреки К-34
     (ADR-125 §3). Правило чинится по замеру, а не по памяти: без лога у проекта нет ни одной
     цифры о тяжести ответов (ADR-123 §4).
  Разделение выхода на текст к Owner и машинную часть сохраняется: в машинной части коды
  свободны, её адресат — файл и следующая роль. Нарушение — дефект ответа независимо от
  точности содержания. Мотив, дословно от Owner: «хотелось бы чтобы все было кратко,
  лаконично, без воды, только тезисы с небольшим пояснением о чем речь, твой анализ
  вариантов и рекомендации». Основание: ADR-074; повод — три сессии подряд с хвостовым
  блоком, который Owner не читает.

- **К-40. Решение Owner выходит accepted сразу.** Запись журнала, все решения которой

  приняты Owner внутри сессии, выходит в статусе `accepted` и несёт секцию «Решение Owner»

  с датой, ссылкой на развилку и дословной цитатой реплики. Запись, где хотя бы одно решение

  принято ролью, и любая запись класса PROCESS выходят `proposed`; сомнение трактуется в пользу

  `proposed`. Фактура роли (цитаты корпуса, выводы хардчека, адреса, расчёты) решением не

  считается. Нет секции при статусе `accepted` — Applier коммит не создаёт. Введена ADR-085.

- **[proposed] К-41. Документ наружу — опора для сверки, а не летопись переписки.** Документ,
  уходящий подрядчику или иной внешней стороне, излагает требуемое поведение системы и дельту
  против выданного адресату задания: по нему сверяется реализация и заводятся задачи на
  расхождения. Слово «канон» здесь не употребляется во избежание путаницы: в К-2 канон — слой L0
  против документации подрядчика, а речь идёт о производном документе.
  Утверждение о НАШЕЙ переписке в такой документ не входит — ни о прошлой («что и когда мы
  прислали, обещали, готовили досылкой, не успели прислать, прекращаем присылать»), ни о будущей
  («ответ пришлём», «вышлем позже»): для приёмки оно бесполезно, истинность его требует носителя
  в отправленном (К-1, К-30) либо будущего действия, и ломается при каждой правке формулировки.
  Остаются три вещи: ссылка на выданное задание (без неё дельта не читается), внесённый записью
  ответ адресата и утверждение о текущем комплекте, обеспеченное связкой порядка отправки.
  Проверяется прогоном перед отправкой; форма команды — ADR-109 §3, локаль по К-35, вердикт по
  каждому совпадению по К-27, вывод строками по К-28. Объём `tools/package_check.sh` правило не
  расширяет: это правило роли. Повод: шесть случаев одного класса за три захода ревью плюс
  седьмой, найденный в будущем времени четвёртым заходом. Основание: ADR-108 §1, решение Owner
  2026-08-08; дополнена ADR-109 §3 и §6.

- **К-42. Упаковка смысла: расколотый орех.** К-39 задаёт форму ответа, К-42 —
  его содержание. Ответ передаёт готовый смысловой результат, а не сырьё, из которого
  читатель собирает результат сам. Главный тест перед выдачей: если читателю после абзаца
  нужно самому сопоставить факты, восстановить причинность и сформулировать вывод, который
  роль уже могла сформулировать, — ответ упакован неверно и выдаче не подлежит.
  1. **Вывод раньше доказательства.** Смысловой блок открывается результатом; фактура идёт
     после вывода как подтверждение. Порядок «факт → факт → факт → поэтому» запрещён.
     Обязательно для рекомендаций, сравнений, диагностики, разбора ошибок, результатов
     проверки и предложений о следующем шаге.
  2. **Связь формулирует роль, а не читатель.** Вывод из сопоставления двух мест пишется
     самим сопоставлением одной фразой («формулировка раздела 0 требовала строгой
     одновременности, ADR-103 §3 её допускает разной»), а не выкладыванием обоих мест рядом.
  3. **Результат вместо журнала действий.** «Сделал X, потом нашёл Y, потом проверил Z» —
     только если Owner просил журнал. Иначе последовательность действий сворачивается в
     «что в итоге получилось и что это значит».
  4. **Числа только работающие.** Число выводится, если оно меняет вывод, нужно для решения
     Owner, проверяет существенное утверждение либо задано Owner как критерий приёмки.
     Остальные агрегируются во фразу («все заявленные проверки пройдены, изменений вне
     согласованных классов нет»). К-22 и К-28 этим не ослаблены: они требуют, чтобы число
     имело носитель и было проверяемо, а не чтобы оно печаталось в текст к Owner.
  5. **Один абзац — одна операция:** результат, либо причина, либо риск, либо изменение,
     либо действие, либо исключение. Цепочка «факт → исключение → ссылка → встречное
     условие → вывод» переписывается как «проблема → причина → решение → эффект».
  6. **Термин работает или исчезает.** Код, номер записи, имя файла остаются в тексте к
     Owner, если читатель что-то понимает благодаря им. Иначе убираются либо уходят в
     машинную часть. Точность демонстрируется выводом, а не плотностью ссылок.
  7. **Развилка и рекомендация не прячутся в конце** — они в шапке (К-39 §1, К-25).
     Первые 20-30% ответа уже несут главное.
  8. **Визуальная структура читаемостью не считается.** Заголовки, нумерация, маркеры и
     термины сами по себе доказательством упаковки не являются; критерий один — сколько
     мыслительной работы осталось читателю.
  Четыре грубых класса проверяются машинно, но строгость у них разная (ADR-123 §1, разведена
  ADR-125 §1). ВОЗВРАЩАЮТ ответ роли два: вывод, спрятанный в последнюю строку (пункт 1), и
  журнал действий от трёх шагов подряд (пункт 3). ПРЕДУПРЕЖДАЮТ, не возвращая, ещё два: строка
  с пятью и более числами при дроби (пункт 4) и четыре с лишним кода проекта в одной строке
  (пункт 6) — оба неотличимы от содержания, которого требуют К-36 и К-28, поэтому их вердикт
  идёт в замер, а решение остаётся за ролью. Остальное решается суждением: его разбирает судья
  `tools/hooks/answer_judge.sh`
  в ПРЕДУПРЕДИТЕЛЬНОМ режиме — ответ не блокируется никогда, вердикт идёт в замер, потому что
  судья недетерминирован и ложный блок дороже пропущенного дефекта (ADR-123 §2). Что не поймали
  ни проверка, ни судья, находит Reviewer либо Owner возвратом ответа. Мотив, дословно от Owner 2026-08-10: «это
  читать сложно, практически невозможно, отнимает много ресурсов расшифровать»; «текста
  всегда много в то время как столько не надо». Основание: ADR-122 §1; хвост переиздан ADR-125 §1 (два признака из четырёх предупреждают, не возвращая).

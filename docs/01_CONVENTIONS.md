# CONVENTIONS

- **К-1. Доказательность.** Ни один вывод не имеет статуса CONFIRMED без цитаты из L3-снапшота с прямым побайтовым доступом (SHA + файл + строки). Пересказы третьих лиц доказательством не являются.
- **К-2. Приоритет канона.** Конфликт L0 vs L3 трактуется как дефект документации подрядчика. Изменение L0 — только через ADR.
- **К-3. Immutable снапшоты.** L3-файлы после коммита не редактируются. Новая версия документа = новый файл с датой. Diff строится машинно от снапшота.
- **К-4. Минимальная достаточность.** Артефакты (Knowledge Graph, Bounded Context Map и пр.) вводятся только при доказанной необходимости, не «по лучшим практикам».
- **К-5. Протокол KB.** Из Master KB без подтверждения используются только секции [1], [2], [9]. Остальное — тезис агента → явное подтверждение/корректировка владельца в сессии.
- **К-6. Скрипты.** Все скрипты — единый copy-paste-ready bash-блок без ручных плейсхолдеров. Каждое значение, известное из контекста сессии, репо, брифа или памяти проекта (пути, SHA, имена файлов, ID, пороги, адреса), подставляется в скрипт литерально. Значение неизвестно → `CONTEXT GAP` и стоп; плейсхолдер вместо значения запрещён. Единственное исключение — launch-строки промтов: SHA сессии подставляет Owner в момент запуска, слот `<SHA>` помечен явно.
- **К-7. Оракул 1С.** Статусы подтверждения: CONFIRMED-DOC (видно в тексте ТЗ) / CONFIRMED-FACT (подтверждено List.kg). Отсутствие в ТЗ = «подрядчик не обязан», а не «система так не делает».

- **К-8. Session-блок обязателен.** Любая сессия (Business/Architect/Executor) закрывается одним session-блоком по 04_SESSION_PROTOCOL. Незакрытая сессия = потерянное знание.
- **К-9. Verify-гейт.** После каждого apply-коммита Owner запускает `bash tools/verify.sh`. RED → следующая сессия начинается с починки; новые задачи не стартуют.
- **К-10. SHA сессии.** Агент работает только по commit-SHA, приложенному Owner. SHA не приложен → агент обязан запросить, чтение main запрещено.
- **К-11. Только клон.** Правки и загрузки в репо — только через локальный клон и apply-скрипты. Веб-интерфейс GitHub для изменений запрещён: создаёт расходящиеся истории (инцидент 2026-07-18).
- **К-12. Санкционированные исключения verify.** Изменение immutable-зоны допускается только при явном решении в сессии; verify для такого коммита запускается как `ALLOW_RAW_CHANGE=1 bash tools/verify.sh`. Категории «ожидаемый RED» не существует: либо GREEN, либо починка.
- **К-13.** — номер аннулирован (ADR-014). Конвенция под этим номером была предложена в сессии
  `arch_phase5_waves_briefs` (2026-07-23) и утрачена вместе с чатом; восстановлению не подлежит.
  Номер не переиспользуется.
- **К-14. Недоступность ≠ отсутствие.** HTTP 404 по угаданному пути, лимит API, ошибка сети и любой
  другой отказ доступа означают «не установлено», а не «файла нет». Вывод об отсутствии артефакта
  допускается ТОЛЬКО из авторитетного листинга (`git ls-tree` от Owner) или из документа, который
  обязан его перечислять. Косвенный вывод об отсутствии не может служить основанием ADR, приоритета
  или задачи; при недоступности — `CONTEXT GAP` и запрос листинга. Основание: инцидент 2026-07-23
  (OQ-05), ADR-014.
- **К-15. Предложенное коммитится.** Proposed-решение вносится в целевой файл в том же apply-коммите
  со статусом `proposed` (ADR — `**Статус:** proposed`; конвенция — префикс `[proposed]`), а не
  выводится списком в чат. Апрув Owner меняет только строку статуса (механика — ADR-016). Ни одно
  решение проекта не существует вне репо. Основание: ADR-014.
- **К-16. Человеческий язык.** Главное правило любой роли и любой сессии, выше остальных дисциплин по приоритету изложения. Пиши так, чтобы уставший человек понял с первого прохода: короткие предложения, обычные слова, без внутреннего жаргона ролей, фаз и режимов. Порядок подачи: что нужно от Owner → какие есть варианты → какой лучше и почему. Рекомендация по развилке выносится отдельной строкой, а не прячется в конце абзаца. Проектные термины (P-xx, ADR-xxx, К-x, L0–L3, BQ/OQ) употреблять можно, но при первом появлении в ответе пояснять одной фразой. Формулировка, которую нужно перечитывать дважды, считается дефектом ответа независимо от её точности.
- **К-17. Стоп при недоступности файла.** Если хотя бы один файл из обязательного контекста роли или из Context-to-load брифа не открылся (404, лимит API, ошибка сети, пустой ответ) — сессия останавливается немедленно. Агент называет точный путь, точный URL, по которому пробовал, и просит Owner прислать содержимое файла в чат. Продолжать «по остальным файлам» и достраивать картину запрещено; вывод об отсутствии файла тоже запрещён (К-14). Работа возобновляется только после того, как Owner прислал содержимое либо явным решением снял файл с обязательного списка.
- **К-18. Ссылка на файл — литеральный raw-URL.** Голый путь (`prompts/architect.md`, `docs/00_STATE.md`) инструкцией на чтение не является: агент не находит его локально и уходит искать в поисковике. Любой файл, который агент обязан прочитать, указывается полным URL вида `https://raw.githubusercontent.com/ilyasbazarov/dom-prorab-ecom-arch/<SHA сессии>/<путь>`. Путь без URL допустим только как ссылка для человека. Ссылки вида `github.com/.../blob/...` запрещены: это HTML-страница, а не файл, и она обычно пиннится к чужому SHA.- **К-19. Контекстная диета и синхронизация.** В обязательный контекст ролей входит docs/02_ADR_INDEX.md вместо полного docs/02_ADR_LOG.md; полный текст конкретного ADR поднимается точечно по номеру. Каждый append ADR в лог сопровождается строкой индекса ТЕМ ЖЕ коммитом. docs/00_STATE.md держит только открытое (open / DEFER / в работе); полностью закрытая строка переносится в docs/00_STATE_ARCHIVE.md дословно тем же коммитом. Архив и полный лог читаются точечно по ID. Основание: ADR-027; базис — holika ADR-064 @ c229bb7.
- **К-20. FILE-строка.** Первая строка каждого docs/NN_*.md и CLAUDE.md — литеральная `# FILE: <путь от корня>`. Агент при чтении сверяет её с тем, что открывал; несовпадение = `СОДЕРЖИМОЕ НЕ ТО: <файл>` и стоп. Проверяется pre-commit хуком. Основание: ADR-027; базис — holika ADR-054.
- **К-21. Claude Code-сессии.** Внутри Claude Code репо читается с локального диска; SHA сессии фиксируется `git rev-parse HEAD` и используется в цитатах файл@SHA:строки. Старт — по CLAUDE.md (чистое дерево, обязательный контекст, самотест хука до первого коммита). Session-блок кладётся в описание коммита. `git push` — только по явной команде Owner. К-10 и К-18 остаются законами чат-сессий и на Claude Code-сессии не распространяются. Основание: ADR-029.
- **К-22. Вывод без артефакта не существует.** Любой замер, листинг, выгрузка или численный вывод, на который опирается решение, кладётся файлом в репо той же сессией: сырьё — `reference/`, брифы — `briefs/`, решения — журнал решений. В docs/00_STATE.md число упоминается только со ссылкой на файл; голая цифра без ссылки — незакрытая задача. Основание: ADR-032.
- **К-23. Аномалия заводится строкой немедленно.** Любое необъяснённое поведение системы — строка в §Открытые вопросы docs/00_STATE.md в момент обнаружения, независимо от влияния на результат и от того, устранено ли следствие. Закрытие — только по установленной причине либо явным решением Owner «принимаем риск» (тоже фиксируется). Фиксация в коммит-сообщении фиксацией не считается. Основание: ADR-032.
- **К-24. Протокол снятия гейта.** Обход гейта целостности (`--no-verify` и любой аналог) допускается только при одновременной записи в docs/00_STATE.md трёх полей: причина; что осталось непроверенным; срок починки. Нет любого из трёх — обход запрещён, работа откладывается. Основание: ADR-033.
- **К-25. Развилки — отдельным документом.** Развилки Owner подаются отдельным коротким блоком: заголовок, суть выбора, варианты с последствиями, рекомендация отдельной строкой; ответ на развилку не должен требовать чтения ADR целиком. Внутри тела решения развилки не подаются. Основание: ADR-030 §2.
- **К-26. Детерминированное — коду.** Разбор структуры, подсчёт, сверка хешей, проверка формата исполняются скриптом, не моделью; модель применяется там, где нужно суждение. Основание: ADR-030 §5.
- **К-27. Отменяющее решение проверяется сплошным поиском.** Решение, отменяющее или
  переопределяющее понятие (а не двигающее значение), применяется не только по перечисленным
  якорям. Исполнитель прогоняет сплошной поиск понятия по репо, печатает совпавшие строки с
  номерами и вносит в blast radius вердикт по КАЖДОМУ совпадению: «правится» либо «остаётся,
  потому что». Пустая выдача поиска фактом не является. Основание: инцидент ADR-012 → ADR-019/ADR-020.
- **К-28. Критерий формулируется утвердительно и числом.** Не «вывода нет», а «файлов
  кроме заглушки: 0». Пустой вывод результатом не является никогда. Скрипт, выносящий вердикт,
  печатает совпавшие строки с номерами, а не метку PASS/FAIL: метка непроверяема, строки
  проверяемы. Дополняет К-22 и К-26.
- **К-29. Датировка расщеплена.** Имена сессий, брифов и артефактов датируются локальной
  датой. Любой временной ФАКТ в тексте документа пишется в UTC с явным суффиксом Z. Смешение
  даёт уверенные ложные выводы о таймингах прогонов и вебхуков.
- **К-30. Внешний факт существует только записью.** Ответ подрядчика или List.kg,
  полученный голосом, звонком или в мессенджере, фактом не является, пока не внесён в
  l2-registers/contractor_questions.md с датой, автором и дословной цитатой. Статус CONFIRMED-FACT
  (К-7) присваивается только такой записи. Пересказ в сессии доказательством не является (К-1).
- **К-31. Декомпозиция даёт непересекающиеся наборы.** Брифы, предназначенные к
  параллельному исполнению, выпускаются с непересекающимися наборами файлов на запись.
  Пересечение — дефект декомпозиции, а не повод запускать по одной. Поле «Файлы на запись»
  обязательно и машиночитаемо: заголовок, затем маркированный список, путь первым токеном
  строки. Поле отсутствует или пусто — отказ проверки, а не разрешение.
- **К-32. Приёмка формулы предъявляет разницу до прогона.** Формулируя приёмку правки
  формулы или алгоритма, выпиши обе формулы и предъяви разницу ДО прогона. Ненулевая разница
  входит в приёмку как ожидаемая величина, а не как условие «не изменилось».
- **К-33. Снимки в reference/ не правятся.** Файл, положенный в reference/ как снимок
  внешнего источника или как разбор, после коммита не редактируется. Исправление или новая
  редакция — новый файл с новой датой в имени. Провенанс снимка (строки, байты, sha256 первые
  16 символов) записывается в шапку разбора. Мотив тот же, что у К-3 для l3-external: снимок,
  правимый задним числом, ссылаться на себя не позволяет.
- **К-34. [proposed] Признак правила-останова проверяется негативным прогоном.** Если смысл
  правила — остановить работу при наступлении условия X, его признак исполнения формулируется
  по ветке останова и проверяется намеренным прогоном при наступившем X. Положительная ветка
  («работа пошла, X не наступило») признаком не является: она наступает всегда и не
  удостоверяет ничего. Результат негативного прогона кладётся файлом (К-22); без файла
  признак не считается проверенным. Исход «роль назвала нарушение и продолжила работу»
  засчитывается как провал прогона, а не как частичный успех. Основание: ADR-046; поводы —
  ADR-041 и ADR-045, чьи признаки описывали положительную ветку, отчего правило трижды не
  сработало в поле.
